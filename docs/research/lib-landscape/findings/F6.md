**A1 note — what a part receives (variant/state props).** Park UI and Chakra are identical here: `withProvider`
(root) accepts recipe **variant props**; `withContext` (child slots) receives **none** — it reads resolved styles
from a React context the provider populated. Panda's own docs: "`withContext` … **does not accept variant props
directly, but gets them from context**." A child part that needs a variant value inside the DOM must opt in via
`forwardProps: ['orientation']`. Source: [panda jsx-style-context](https://panda-css.com/docs/concepts/jsx-style-context).

### A3 — THE ANSWER TO THE CORE QUESTION: how a token change propagates to a restyled part

**The mechanism is not class merging. It is whether the recipe references a token *name* or a *literal value*.**
Every kit that survives a restyle does so because of indirection, and the three grades are:

> **Correction added after measurement (2026-09-28).** The ladder below originally started at Grade 1. A
> measurement against Astryx core 0.3.0 — reported independently by `LibLandscape.DataLayoutWorker` and
> `Main`, both from reading `core/src/`, not from the docs — found a case **below Grade 1**: core assigns
> `el.style.backgroundColor = selectedBgColor` on selected table rows, i.e. an **imperative inline style**.
> That outranks *every* cascade layer, so **Grade 3 does not survive it either**, and the table's "strongest
> grade" framing was wrong. Grade 0 is now row 0. See the caveat under the table.

| Grade | Mechanism | Who does it | What happens to a restyled part | Source |
|---|---|---|---|---|
| **0 — below the ladder** | A **specific property** set by imperative DOM code (`el.style.prop = value`) rather than by any stylesheet. | Astryx core 0.3.0 selected table rows (`el.style.backgroundColor`) | **Per-property, NOT per-element.** An inline style outranks every cascade layer, so no stylesheet can re-set **that property** on that element. A stylesheet rule on **any other property of the same element still applies and still paints.** | inline-assignment census across `core/src/`, measured by `Main` 2026-09-28 — **not independently re-measured by this worker** |
| **1 — weakest** | Recipe writes the property directly; token is a plain value substitution. | Chakra v2-style `styleConfig` (now removed) | Changing the token changes the value everywhere the part is **not** overridden. A part the consumer restyled **loses the token change entirely** for every property it touched. | [chakra v3 migration](https://chakra-ui.com/llms-v3-migration.txt) — `styleConfig`/`multiStyleConfig` removed in favour of recipes |
| **2 — token-name + cascade layer** | Recipe writes `background: var(--colors-blue-subtle-bg)` and lives in `@layer recipes`; the consumer's override lives in `@layer utilities` or an unlayered sheet. | Park UI, Chakra v3, Panda | **Property-scoped.** A consumer override of `padding` does **not** shadow `background`. Repinning the token still repaints the part. A consumer who overrides *the same property* shadows that one property and nothing else. | [panda cascade-layers](https://panda-css.com/docs/concepts/cascade-layers) · [park button.ts](https://raw.githubusercontent.com/chakra-ui/park-ui/main/packages/preset/src/recipes/button.ts) |
| **3 — strongest, and the one Astryx is missing** | Per-component **local variable indirection**: the component declares `--button-bg: var(--accent)`, then uses `background: var(--button-bg)`. The consumer overrides `--button-bg` on one instance; the global token is untouched; every other part still tracks the token. | HeroUI v3 | Repin `--accent` → every part repaints. Override `--button-bg` on one node → that node detaches, per-instance, and nothing else moves. **Local override and global propagation coexist because they are different variables.** | [heroui v3.0.5 release notes](https://heroui.com/en/docs/react/releases/v3-0-5) |

> **The wash/ring discriminator (added after `Main`'s per-property correction, 2026-09-28).** Grade 0 was
> first written here as a blanket "no stylesheet can reach it". That is **false**, and the correction is the
> most transferable thing in this section. The inline-assignment census over `core/src/` is:
> `23 .style.width · 13 .style.maxWidth · 13 .style.insetInlineStart · 9 .style.top · 8 .style.minWidth ·
> 8 .style.left · 8 .style.aspectRatio · 7 .style.userSelect · 2 .style.color ·
> 2 .style.borderRadius · 2 .style.backgroundColor`, and **`grep -rn "style.boxShadow" core/src/` → ZERO.**
>
> So the two affordance channels land on opposite sides of the blocker, and treating them as one problem is
> what made one look like two:
>
> | Channel | Property | Reachable? | Why |
> |---|---|---|---|
> | **Wash** | `background-color` | **No** | core assigns it inline on selected rows. Beating it needs `!important` (banned by our own gate) or a core change (deferred by the version ruling). |
> | **Ring** | `box-shadow` | **Yes** | core **never** assigns it inline, anywhere. Independent properties on one element, so a stylesheet ring applies and paints over whatever background core set. |
>
> **General form, and it is the part to carry forward: an imperative-style blocker is scoped to the property
> that was claimed, never to the element.** "Core owns this row" is a false premise; "core owns this row's
> `background-color`" is a true one. The first framing makes an adjacent, entirely-open channel look closed,
> and the cost of believing it is a design decision escalated as a technical blocker. **Before declaring a
> substrate-owned state unreachable, read which property it actually claimed.**

Grade-3 primary evidence, verbatim from the HeroUI v3.0.5 release note (2026-05-15):

```css
/* packages/styles/components/button.css */
.button--primary {
  --button-bg: var(--accent);
  --button-bg-hover: var(--accent-hover);
  --button-fg: var(--accent-foreground);
}
```

**This is the single most transferable mechanism in this angle.** Astryx ships `--color-*` tokens consumed
directly by core; there is no per-part local alias between the global token and the property. A consumer
restyling a part therefore shadows the token at the property level, not at a named local alias.
Recommendation: a per-part local alias layer. **NEEDS-HUMAN-APPROVAL: the alias token naming scheme and the
first part to receive it.** Do not invent the name.

> **Caveat on the Grade-3 recommendation (added with the Grade-0 correction).** Grade 3 is the strongest
> *stylesheet-level* mechanism and remains the right adopt for Astryx — but it is **not** a fix for
> Grade 0. A local alias (`--button-bg: var(--accent)`) resolves *inside* the cascade, so an inline
> `background-color` on the same element outranks it exactly as it outranks the token. Adopting Grade 3 to
> solve a selected-row wash would be solving the wrong grade: the blocker is that **core owns the property
> imperatively**, not that the kit lacks a per-part alias. The two fixes are not interchangeable, and only
> one is available without a core change.
>
> First-party precedent, from a library that hit this exact hazard: Mantine documents that its `styles` prop
> is an inline style attribute and therefore "higher specificity than classes, so you will not be able to
> override them with classes without using `!important`" — which is why `classNames` is the recommended path
> and `styles` is explicitly discouraged. Mantine's guidance is the general rule: **the layer that sets a
> property imperatively owns it, and the consumer must style through a channel that layer does not write.**
> [mantine styles-api](https://mantine.dev/styles/styles-api/) · primary
>
> Corollary, and it is the reason a `SCENE_HUES`-style **type union** is the right shape for a stated
> prohibition: a union does what a comment cannot. The same shape recurs independently in this wave — a
> header rule in `shared/scene-tile.tsx:5-6` did not stop its own callers, and a prose rule in a module
> header cannot outrank a free-form `string` prop. **A rule stated in prose is a request; a rule stated in
> the type is a compile error.** Where a prohibition is load-bearing, enforce it at the type boundary.

### A4 — How each kit derives states (relevant to token propagation in dark-only)

| Kit | Derivation | Source | Conf |
|---|---|---|---|

| Park UI | States are **condition aliases** on data attributes, not variant props: `checked: '&:is(:checked,[data-checked],[data-state=checked],[aria-checked=true],[data-state=indeterminate])'`, `on: '&:is([data-state=on])'`, `invalid: '&:is(:user-invalid,[data-invalid],[aria-invalid=true])'`, `hover: '&:not(:disabled):hover'`, `pinned: '&:is([data-pinned])'`, `light: ':root &, .light &'`. | [park conditions.ts](https://raw.githubusercontent.com/chakra-ui/park-ui/main/packages/preset/src/theme/conditions.ts) | primary |

**A4 → dark-only survivability verdict:** all four survive a dark-only pin. Park UI is the clearest precedent —
its own accent palettes are already mode-agnostic (`_light` == `_dark`); only the *neutral* alpha steps fork.
Adopting Park's structure would mean our brand's token file carries **no** `light-dark()` pairs and **no**
dark condition, which is exactly the `pin()`-every-tuple model the brief already holds.

### B12 — Counter-angle synthesis: three failure classes, not seven libraries

| Class | Mechanism that fails | Instances | Astryx exposure |
|---|---|---|---|
| **1 — Emission drift** | The library changes how it emits its own rules, and every consumer override silently inverts. | Mantine 7.6.0 `:where()` (B3b); HeroUI `text-*`/tailwind-merge (B7); HeroUI v2 TW4 empty selectors (B7c) | Astryx pins a static `theme.css`/`tokens.css`; exposure is **low** for emission drift, **high** for the namespace-collision half of B7. |
| **2 — Token escape hatch** | A value that should be a token is hard-coded in component source; the theme can no longer reach it. | shadcn `bg-black/80` overlay (B6b); Astryx `ToastViewport zIndex:500` (F3) | **Live.** This is a gate-able defect class, and `check.ts` is where it belongs. |
| **3 — Mode-switch machinery as a maintenance tax** | Supporting a light/dark fork costs a provider, a storage layer, an SSR nonce path, a pre-hydration script, and a third-party dependency — all of which a dark-only brand pays for nothing. | Mantine localStorage + `ColorSchemeScript` + postcss mixins (B4b); Chakra → `next-themes`, stale since 2025-03-11 (B5, B5b) | Astryx is already dark-only, so it pays **none** of this. This is an argument for the brief's "dark-only, do not re-litigate" ruling, now with a primary-source cost attached. |

**Load-bearing counter-findings for the report:**
1. **B3b is the strongest evidence in this file** for the report's own question. A library that documented
   "Styles API overrides the component" had that guarantee broken by a `:where()` refactor in a patch
   release. Any recommendation to Astryx that leans on specificity ordering needs a gate proving the ordering
   still holds, not a comment asserting it.
2. **B7 is the strongest warning.** Silent style loss from a *name* collision. Astryx's `tokens.css` is a
   flat unlayered mirror, so there is no layer to absorb a collision.
3. **B8 and B9 correct two widely-repeated claims.** "Reakit is dead" and "Recharts is unmaintained" are both
   false against the primary record. Anything in the report that repeats them must be fixed.
4. **B1 is the most directly Astryx-relevant bug.** A brand kit with 45 templates controls overlay open state
   programmatically — that is *precisely* the trigger condition. Astryx ships no overlay of its own, so this
   is a **do-not-copy** finding rather than a live defect, but it is the reason a kit-authored overlay would
   need its own controlled-open test.

   by HTTP-probing 36 candidate doc paths and counting 200s; `radix-ui.com/primitives` is client-rendered, has
   no `llms.txt` (404), and the GitHub contents API rate-limited. The slug list probed was:
   `accordion alert-dialog aspect-ratio avatar checkbox collapsible context-menu dialog dropdown-menu form
   hover-card label menubar navigation-menu one-time-password-field password-toggle-field popover progress
   radio-group scroll-area select separator slider switch tabs toast toggle toggle-group toolbar tooltip`

   primitive slot` (all 404). **A 30th-or-fewer primitive not in that candidate list would not be counted.**
   Radix is `PrimitivesWorker`'s angle; this is a cross-check number, not a definitive census.
2. **No primary-source "migrating away from X" postmortems were found** for any of the four kits. Every
   counter-angle item is therefore a *library-side* record (own issues, own changelogs, own docs) — which the
   brief flagged as the underrepresented direction, but the vendor-side bias runs the *other* way here: these
   are maintainers reporting their own defects, not users reporting pain. Reddit/dev.to hits existed and were
   **deliberately not cited** as load-bearing. The one genuinely user-framed source used is the shadcn #1807
   requester, who is a shadcn community member, and his diagnosis is quoted as *his* diagnosis.
3. **Panda's `cx` internals not read at source.** The claim that `cx` dedupes rather than concatenates is
   inferred from the Panda docs' utility-class-override examples and the generator's use of it, not from
   reading `cx`'s implementation. Sufficient for the conclusion (cascade layer decides precedence, not
   `cx`), but the function itself is unverified.
4. **Chakra v3's `createSlotRecipeContext` implementation not read at source** — only the `d.ts` (which 404'd
   on the version probed) and the theming guide's usage examples. The className merge order inside Chakra's
   `withProvider`/`withContext` is therefore **unverified**. Given Mantine's identical failure (B3b) is
   specificity-based rather than order-based, this is unlikely to change the conclusion, but it is a gap.
5. **No HeroUI GitHub issue was independently reproduced.** B7c rows report filed symptoms (empty generated
   selectors, unapplied colour/radius). We did not build a repro. B7, by contrast, is a **maintainer-confirmed
   root cause with a named PR and a linked issue**, and is the only HeroUI failure row that should be treated
   as settled.
6. **Mantine v9 specifics not surveyed.** All Mantine material is from the current `/llms/` docs (serving

   `unstyled` on any provider or slot (documented, and present in the generator's `getResolvedProps`), but no

   **unverified**. It is the cleanest "opt this part out of the recipe entirely" mechanism in the set and is
   a candidate Astryx adopt if it turns out to be live.
