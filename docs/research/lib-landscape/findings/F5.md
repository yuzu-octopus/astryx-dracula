# F5 — A11y & interaction correctness (React Aria, Floating UI) + cross-cutting truncation / tooltip / empty-state

Date fetched: 2026-09-28. Depth: deep.
All rows: claim / source / confidence. Confidence: `primary` = official source or first-party code read directly; `secondary` = vendor search/answer layer; `speculative` = inference marked as such.

---

## Angle

React Aria Components (Adobe) as the reference implementation for keyboard/focus correctness + Floating UI's focus manager; plus the CROSS-CUTTING problem of **truncation / tooltip / empty-state** across Radix, shadcn, Mantine, Chakra, React Aria, HeroUI, Base UI.

Question: extract React Aria's collection model, `useSelectableCollection`/`useSelectableItem`, `useFocusRing`/`useHover`, `FocusScope`, `PressResponder`/`Keyboard`; then answer what would measurably improve if Astryx adopted the boolean-hook-plus-attribute pattern.

F1. **Why the delay family exists at all** (React Aria's own statement, primary): "Tooltips appear after a 'warmup' delay when hovering, or instantly on focus. Once a tooltip is displayed, other tooltips display immediately. If the user waits for the 'cooldown period' before hovering another element, the warmup timer restarts." — https://react-aria.adobe.com/Tooltip
F2. React Aria's in-source comment is a gift for the report: `const TOOLTIP_DELAY = 1500; // this seems to be a 1.5 second delay, check with design`. Adobe's own 1500 is a *drafted* number, not a derived one. The 300/700 pair in Radix is likewise conventional, not measured. **Nobody in this landscape can cite a measurement for their tooltip delay.**
F3. React Aria's warmup also drives **animation**: `shouldSkipAnimation` is set when swapping tooltips during warmup, so the second tooltip appears with no enter transition. Radix's equivalent is a `stateAttribute` of `'closed' | 'delayed-open' | 'instant-open'`. Base UI's is `data-instant: 'delay' | 'dismiss' | 'focus'`. Three independent inventions of the same three-state axis.
F4. Only one tooltip open at a time is enforced by a module-level `tooltips` map in react-stately, and by `isPointerInTransitRef` + a `document` CustomEvent `tooltip.open` in Radix.
F5. Radix's `skipDelayDuration` is a **provider**-level concept (one group for a whole app); React Aria's warmup is **module-global** with no opt-out. Base UI makes it a `Tooltip.Provider` prop.
F6. shadcn deliberately sets `delayDuration = 0`, overriding Radix's 700 — a 23-year-old toolchain default (tooltip on tab-through) is wrong for keyboard users who tab through a toolbar, but right for pointer users scanning. **[INFERENCE — speculative]** The 0 is a deliberate, opinionated override, not an oversight; shadcn does not document why.

### G. Cross-cutting — truncation and `min-width: 0`

| # | Claim | Source | Confidence |
|---|---|---|---|
| G1 | **The normative reason a truncated string cannot shrink in a flex child.** CSS Flexbox L1 §4.5: `auto` is the new initial value of `min-width`/`min-height`; "the used value of a main axis automatic minimum size on a flex item whose computed overflow value is **non-scrollable** is its content-based minimum size; for main-axis scroll containers the automatic minimum size is zero, as usual." | G2 | The spec states the cure directly: "To change this, set the `min-width` or `min-height` property" (§7.1, flex-shrink discussion). | G3 | Same section, for the grid case: a content-based minimum size "causes the box's size in that axis to become indefinite" for intrinsic-size purposes, so percentage children resolve against an indefinite size. | same as G1 | primary |

### J. The answer: what measurably improves with the boolean-hook-plus-attribute pattern

**J1 — The measured baseline (this is the finding, not a recommendation).** Core 0.3.0 emits **no `data-*` state hooks anywhere.** The honest sentence is scoped to `data-*`: core is **not** devoid of state attributes — J8 shows it emits `aria-selected` imperatively on selected table rows, and J7 counts 11 `aria-selected` plus ~54 `aria-disabled`, ~41 `aria-expanded`, ~26 `aria-checked` emissions. **What core does not emit is the `data-*` half** — and it is the `data-*` half a stylesheet can select on. Measured across `node_modules/@astryxdesign/core/src` excluding tests:
- `data-state`, `data-hover`, `data-selected`, `data-checked`, `data-open` → **0 occurrences** (the single `data-state` hit inside `DateInput.tsx:677` is inside a *comment*).
- The full `data-*` inventory is `data-w=` ×66, `data-astryx-live-region=` ×31, `data-variant=` ×14, `data-astryx-media=` ×14, `data-custom=` ×10, `data-toast-id=` ×6, `data-autofocus=` ×6, `data-astryx-theme=` ×6, plus assorted one-offs. **Every one of them is either a render-prop plumbing attribute or a data attribute — none encodes a visual state.** *(Amended 2026-09-28: this file originally said "no state-attribute mechanism at all", which was an overstatement. It was true of `data-*` and false of ARIA. An earlier relay of this finding also dropped `data-custom=` ×10 from the inventory; it is restored above. See J8.)*
- Interactive state is additionally passed as **props the consumer must remember**: `Table.tsx:70 hasHover?: boolean` (@default `false`), `density`, `isStriped`, `verticalAlign`, `textOverflow`; `Tooltip.tsx:124 hasHoverIndication?: 'auto' | boolean`.
- Confidence: primary (local, measured). **The narrowing to `data-*` is itself load-bearing and should not be relaxed in the report** — it is the difference between "no mechanism" and "no `data-*` mechanism, but a large ARIA one", and those imply different fixes.

**J2 — That baseline explains a defect another worker already found.** Main reports `templates/documentation-design.tsx:638`, a Table missing `hasHover`. J1 gives the mechanism: `hasHover` is a **defaulted, optional, silently-false prop on a compound parent**. Nothing in the render tree signals its absence — no attribute, no warning, no required prop. A `data-hover` attribute emitted by `TableRow` cannot be forgotten at a call site, because the component emits it. **This is the falsifiable, measurable claim: the boolean-attribute pattern eliminates the entire class of "consumer forgot a defaulted state prop" defects, and that class is non-empty in this repo today.**

**J3 — Why the pattern is unusually cheap for Astryx specifically.** StyleX compiles `stylex.create` to static CSS at build time. A selector keyed on a data attribute compiles to a real class in the stylesheet; the DOM carries the semantic truth, the stylesheet carries the visual decision. The brand kit already owns a full unlayered CSS mirror (`tokens.css`), so a `data-*` selector is styleable from the kit without touching core. **[INFERENCE — speculative on the "unusually cheap" framing; the StyleX build-to-static-CSS fact is from the brief, not re-measured here.]**

**J4 — What it does NOT fix, stated so the report cannot oversell it.**
- It does not fix keyboard *correctness*. That is `FocusScope`/`useSelectableCollection` territory (C1-C4, B4) and is a much larger, riskier adoption than a state attribute. Astryx should adopt the **boolean-returning-hook** half (J1) and decline the **focus-manager** half.
- It does not add visual capability. Every state Astryx can style via `data-*` it can already style via a prop.
- It is not a token change: it introduces no hex, no font, no radius. (Good — it clears the brief's `needs-human-approval` bar with nothing to approve.)

**J5 — The one genuinely new capability React Aria's hooks carry that Astryx has no equivalent of: `useHover` is behaviourally different from CSS `:hover`, and it is not sugar.** A4 (500 ms emulated-event suppression for iOS; synthesized `hoverend` on element removal) is a real defect class — sticky tooltips that never close when their trigger unmounts, and hover states that stick after a tap. Astryx core's `Tooltip` `HOVER_BRIDGE_DELAY = 100` is a partial, tooltip-local fix for exactly the second problem. **[INFERENCE — speculative]** the general form is worth a kit-level hook, the tooltip-local constant is not.

**J6 — Ordering recommendation for the report (proposal, unapproved).** The empty-state and tooltip work is *already* in core (`EmptyState`, `Tooltip` with `delay: 200` / `HOVER_BRIDGE_DELAY: 100` / Escape / `aria-describedby`), and truncation+tooltip is *already* in core (`Text maxLines` + `useTruncation` + lazy Tooltip). The landscape's contribution is therefore **not** "add an empty state" or "add a tooltip" — both would be re-implementations of shipped core. The contribution is narrow and specific:
1. **Adopt**: boolean-state-as-attribute at the row/table level, to kill the defaulted-prop class (J1/J2).
2. **Adopt**: the `min-width: 0` discipline is already core practice (G4) — carry it into the **kit's** shared modules (`shared/*` are the kit's own code and are the only place a new contributor can get this wrong).
3. **Reject**: React Aria's 1500 ms delay (a self-described draft number, F2) and Radix's 700 ms. Core's 200 ms is closer to right for a keyboard-first brand and is a single token change away if the human disagrees.
4. **Reject**: a shadcn-style composable `Empty` — core's `EmptyState` is one component with 6 props and the brand has 10 correct call sites (per Main). Composing it into 6 slots would be a rewrite with no user-visible gain.
5. **Do not re-litigate**: whether truncation needs a reveal mechanism. It does — G6 (I6) is the normative answer and core already implements it.

**J7 — The alias-layer question, answered by measurement. Core's ARIA surface is large and its data-state surface is empty, so a Park-UI-style condition layer is viable for STATE and impossible for HOVER.**

A condition layer written as Park UI writes one (arms including both `[data-state=…]` and `[aria-checked=true]`) styles correctly whichever the component happens to emit, and here only the ARIA arm can ever bind.
- **The hover arm does not exist and cannot be made to.** Hover has no ARIA equivalent, and J1 established core emits no `data-hover`. **A table row's hover state is not reachable by any attribute core emits.** The alias layer closes selection, checkedness, expansion, current, pressed and disabled; it does not close hover, and the brand's ruling-2 hover channel (ring vs wash) therefore cannot be driven by a condition layer at all — it has to be driven by the kit's own CSS against kit-authored markup.

**J8 — RETRACTION, and it is load-bearing. The "hover is unreachable" claim above is false, and the correction is measured, not inferred.**
I asserted that a `TableRow` is not `aria-selected` — that the attribute belongs to `gridcell`, so "the J2 `hasHover` finding cannot be fixed by this mechanism even in principle." That was an inference from ARIA semantics. **It is wrong.** `Table/plugins/selection/useTableSelection.tsx` applies it to the row itself:
```ts
/** Apply or remove selection styling on a <tr> element. */
function applyRowSelectionStyle(el: HTMLTableRowElement, isSelected: boolean): void {
  if (isSelected) {
    el.setAttribute('aria-selected', 'true');
    el.style.backgroundColor = selectedBgColor;
  } else {
    el.removeAttribute('aria-selected');
    el.style.backgroundColor = '';
  }
}
```
The plugin's own header states the design: "Row-level styling (aria-selected, background) uses imperative DOM updates via a ref callback on each `<tr>`… no extra DOM elements and no central element tracking." Core deliberately chose **imperative DOM over a declarative attribute prop** and shipped **no CSS custom property for the selected background** — `selectedBgColor` is assigned straight to `style.backgroundColor` (line not read; presence confirmed at line 131).

Three consequences, all measured:
1. **The SELECTED half of ruling 2 is buildable in the kit's CSS today.** `[aria-selected="true"]` on the `<tr>` is a real, always-present hook on exactly the surface the ruling names — "selected full-width rows". A condition-layer arm for it works with no core change. The premise "the selected half needs a state hook core emits nowhere" is **false**, and if it has gone to the human it should be corrected before it is ruled on.
2. **The HOVER half of ruling 2 is still unresolved, for a different and worse reason than the one I gave.** Not "no attribute exists" — `hover` is now expressible via CSS `:hover` / `:focus-visible` on any element, no attribute required. The real blocker is narrower and it is about layering, not reachability: core sets `el.style.backgroundColor` imperatively on the same element, and an inline style outranks any stylesheet rule from `tokens.css` at equal specificity. So a wash or a ring declared in `tokens.css` loses to core's inline background on selected rows **unless the selected rule is `!important` or core's assignment is removed.** That collides head-on with the zero-`!important` gate in ruling 7, and it is a genuine decision for the human — one nobody has named, because everyone has been reasoning about attribute reachability.
3. `Item.tsx:411,546-547` shows core gating `aria-selected` behind `allowsAriaSelected`, with the comment "aria-selected is only valid on selectable roles (option, tab, treeitem…)" and "aria-selected is invalid on roles that don't permit it (listitem, a bare div)". **So the hook's presence is role-dependent, not universal** — a condition layer arm written as `[aria-selected]` will bind on option-like roles and silently do nothing on `listitem`/bare div. Any per-component binding has to check the role first. Confidence: primary.

**Method note, and it is the wave's own lesson applied to me.** I asserted a fact about core's ARIA output from ARIA knowledge, not from core, and it was the load-bearing claim in my own recommendation. It took one `grep -rn "aria-selected"` to overturn — the same one-command check that caught LibLandscape's three false premises and that the proposed doctrine sentence requires for capability claims. I would not have found it by reasoning harder about the spec; the spec was the thing I wrongly generalised from. Confidence in J7's counts: unchanged, primary. Confidence in J7's *hover claim*: **withdrawn.**

**J9 — SECOND RETRACTION, same day, and it retracts the blocker I myself wrote. The selected RING is not blocked; the selected WASH is. I generalised "inline style beats stylesheet" across properties without checking which property the ring uses.**
Two measurements, both local:
```
Table/plugins/selection/useTableSelection.tsx:131   el.style.backgroundColor = selectedBgColor;
Table/plugins/selection/useTableSelection.tsx:279   const selectedBgColor = colorVars['--color-accent-muted'];
theme/tokens.stylex.ts:26                           '--color-accent-muted': 'light-dark(#0082FB33, #0082FB3F)',
theme/tokens.stylex.ts:146                          export const colorVars = stylex.defineVars(colorDefaults);
```
1. **The collision is per-property, and the ring is a different property from the one core sets.** Core writes an inline `background-color`. Every ring in this brand is an inset **`box-shadow`** (`--shadow-inset-hover: inset 0 0 0 2px …`), and an inline `background-color` cannot override, outrank, or suppress a `box-shadow` on the same element — inline styles win per property, not per element. So a `[aria-selected="true"] { box-shadow: inset 0 0 0 2px … }` arm in `tokens.css` lands on selected rows with no `!important`, no core change, and no collision with ruling 7's zero-`!important` gate. **Gap 13's "both exits blocked" is wrong: for a ring there are no exits to take, because there is no conflict.**
2. **What the collision actually blocks is the WASH** — a `background-color` on selected rows is genuinely core's, and a kit wash loses. That is a real and much smaller constraint: it says selected rows get a *ring* rather than a wash, which is what ruling 2 already specifies. The constraint confirms the ruling rather than blocking it.
3. **And the wash is not even closed, because the colour is a token the kit already owns.** `selectedBgColor` is `colorVars['--color-accent-muted']`, a `stylex.defineVars` entry, not a literal. The kit pins every core colour tuple to a dark hex, so the kit already decides what core paints on selected rows. If a wash were ever wanted, the lever is the token, not the cascade and not `!important`. (The `var(--…)` indirection is StyleX's documented `defineVars` behaviour; I read the definition and the assignment, I did not execute a build to observe the emitted CSS. Confidence: primary for the code; the runtime resolution is documented behaviour, marked as such.)

**Net correction to what went to the human.** The claim "the selected half does not land this wave, both exits blocked" rests on my gap 13 and is **false for the ring**. It is true only for a wash. The correct statement is: selected rows expose `[aria-selected="true"]`, the ring is expressible on a property core does not touch, and the only thing core owns on that element is the background colour — which the ruling does not want to change. **The selected ring can ship in this wave with no new mechanism, no `!important`, and no core change.**

**Second instance of the same mistake, and I am recording the pattern rather than the instance.** J8 and J9 are the same error twice: a claim generalised from a neighbouring property or a neighbouring spec rule, without a measurement of the specific thing. J8 generalised from ARIA semantics; J9 generalised from a correct CSS principle applied to a property it does not govern. The wave's doctrine sentence predicts exactly this — "a rule stated from the evidence in front of you… stops being true one scope out" — and here the evidence in front of me was `el.style.backgroundColor` while the decision in front of me was `box-shadow`. **A measurement of one property is not a measurement of the decision, and I filed it as one twice.**

**X1 — Mantine's tooltip delay: two readings, one is authoritative.**
`web_search` returned a confident "1000 ms default" for Chakra (from the vendor search layer, tagged secondary, citing a changelog). Reading the Zag machine source directly gives `openDelay: 400, closeDelay: 150` in the machine's own `props()` defaults (primary). **Resolution: the machine source wins** — 1000 ms was the historical value; the current default is 400 ms. The secondary answer was not wrong about the past, only about the present. This is exactly the vendor-blog-rot failure the brief's counter-angle warns about, and it is why every number in §F is read from source.

**X2 — Mantine `openDelay` default is genuinely absent, not 250.**
Mantine's `Tooltip.tsx` `defaultProps` object does **not** list `openDelay` or `closeDelay`; they are passed straight into Floating UI's `useHover({delay: {open, close}})`, whose documented default is `0`. Meanwhile Mantine independently ships `TooltipGroup` wired to `useDelayGroup`. So Mantine's *effective* default is 0 delay + no group unless you opt into `TooltipGroup`. Reporting "Mantine defaults to 250 ms" (a commonly repeated claim) is unsupported by either source. **Carried forward: Mantine effective default = 0 ms, group opt-in.** Confidence: primary (both files read), with the caveat that the effective value depends on Floating UI's default, which is documented rather than read from Floating UI's implementation.

**X3 — `PressResponder`: exists, but is not public.**
A search-layer answer and the task brief both treat `PressResponder` as the React Aria press abstraction. The package index shows `PressResponder, ClearPressResponder` exported from `react-aria/private/interactions/PressResponder` — a private subpath — while `Pressable` is exported from the public `react-aria/Pressable`. **Resolution: both are true and the distinction matters.** React Aria deliberately moved press from a context-based responder (`PressResponder`, which any child could consume) to a hook + element (`usePress` / `Pressable`). The transferable mechanism is *`usePress` returns `isPressed` and applies no styles*; `PressResponder` should not be cited as a current public API.

**X4 — Chakra's wrapper vs its machine.**
Chakra's React wrapper supplies only `{lazyMount: true, unmountOnExit: true}`; all timing defaults live in the Zag machine. Two "Chakra tooltip default" answers therefore conflict depending on which layer is read. **Resolution: machine layer wins** (the wrapper demonstrably does not set timing). Anyone reading only Chakra's React source will find no delay value at all.

**X5 — "The APG tooltip example" does not exist.**
Any claim that a pattern follows "the APG tooltip example" is unverifiable: the APG Tooltip page states the pattern has no task force consensus and that its example is still tracked as issue 127 (I14). The pattern's *normative* content (role, `aria-describedby`, no focus, Escape, stays open while the cursor is on trigger-or-tooltip) is solid and is what §I13 cites. **Resolution: cite the pattern, never an example.**

**X6 — WCAG 1.4.13's hoverable condition vs. practice.**
The criterion requires the pointer to be able to move over the additional content. Core satisfies it with a 100 ms `HOVER_BRIDGE_DELAY`; Radix and Mantine satisfy it with a hoverable-content flag / `safePolygon()`. React Aria's non-interactive tooltip does not implement it, and its own docs instead say "Ensure that your UI is usable without tooltips, or use an alternative component such as a PreviewTrigger or a Popover." **Not a conflict, but a fork in the road:** a truncated-string tooltip should NOT be hoverable (it is a *reveal*, not an interactive surface) and core's bridge-delay is arguably the wrong mechanism for that specific use. **[INFERENCE — speculative]** a `Text`-truncation tooltip wants a bridge, and a trigger-icon tooltip wants a polygon. Two different answers to 1.4.13 Hoverable, from one component.
