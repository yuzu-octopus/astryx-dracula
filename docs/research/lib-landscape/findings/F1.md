# F1 — Unstyled primitives & state styling: Radix UI, Base UI (MUI), Ark UI (zag.js), Reakit, Headless UI

## Angle

How the five unstyled-primitive libraries expose component state to CSS, what their focus/keyboard/overlay contracts are,
how they expose slots and composition, and Reakit's real maintenance status from the owner.

All source-file claims below were read directly from the `main`/`master` branch on 2026-09-28 unless noted. Every row carries
its source URL and fetch date.

## 1. State styling — the core question

### 1a. Attribute *value* conventions differ more than the attribute *name* does

All five expose `data-*`. They split three ways on whether a boolean is a **presence attribute** (`attr=""`) or a **valued
attribute** (`attr="true"`), and Radix/Ark are the only two that make one attribute carry *multiple* values.

| Library | Boolean encoding | Verified attribute strings |
|---|---|---|
| **Radix UI** | presence, **empty string**: `data-disabled={disabled ? '' : undefined}` | `data-state`, `data-highlighted`, `data-disabled`, `data-orientation`, `data-side`, `data-align`, `data-placeholder`, `data-radix-menu-content`, `data-radix-popper-content-wrapper` |
| **Base UI** | presence, **empty string for `true`**, stringified otherwise: `if (value === true) props['data-'+k.toLowerCase()] = ''; else if (value) props['data-'+k.toLowerCase()] = value.toString();` | `data-open`, `data-closed`, `data-checked`, `data-unchecked`, `data-highlighted`, `data-disabled`, `data-pressed`, `data-starting-style`, `data-ending-style`, `data-side`, `data-align`, `data-popup-open`, `data-nested`, `data-nested-dialog-open`, `data-scrolling` |
| **Ark UI / zag** | presence for interaction flags, **valued for `data-state`** | `data-state`, `data-highlighted`, `data-disabled`, `data-ownedby`, `data-current`, `data-scope`, `data-part` |
| **Headless UI** | presence, **empty string**: `dataAttributes[`data-${state}`] = ''` | `data-open`, `data-closed`, `data-enter`, `data-leave`, `data-focus`, `data-selected`, `data-selectedOption`, `data-hover`, `data-active`, `data-disabled`, `data-invalid`, `data-autofocus`, `data-headlessui-state` |
| **Reakit** | **no documented `data-*` state contract at all** — state is props | none documented |

**Three findings that matter more than the table:**

1. **Radix's `data-state` is not a boolean, it is a per-component enum, and the value sets are inconsistent across
   components.** This is the single most copyable-and-easiest-to-get-wrong fact in the landscape:

| Radix part | Exact expression | Value set | Source |
|---|---|---|---|
| `Dialog.Trigger` / `.Overlay` / `.Content` | `data-state={getState(context.open)}`, `getState = open ? 'open' : 'closed'` | `open` \| `closed` | dialog.tsx |
| `Popover.Trigger` (:165), `Popover.Content` (:492) | `data-state={getState(context.open)}`, `getState = open ? 'open' : 'closed'` | `open` \| `closed` | popover.tsx |
| `Collapsible` / `.Trigger` / `.Content` | `getState(open) => 'open' : 'closed'` | `open` \| `closed` | collapsible.tsx |
| `Tabs.Trigger` / `.TabsContent` | `data-state={isSelected ? 'active' : 'inactive'}` | **`active` \| `inactive`** | tabs.tsx |
| `Checkbox.Trigger` | `getState(checked) => isIndeterminate ? 'indeterminate' : checked ? 'checked' : 'unchecked'` | **`checked` \| `unchecked` \| `indeterminate`** | checkbox.tsx:443 |
| `Switch.Trigger` / `.Thumb` | `getState(checked) => checked ? 'checked' : 'unchecked'` | `checked` \| `unchecked` | switch.tsx:419 |
| `Tooltip` | `stateAttribute: 'closed' \| 'delayed-open' \| 'instant-open'`, `open ? (wasOpenDelayedRef.current ? 'delayed-open' : 'instant-open') : 'closed'` | **`closed` \| `delayed-open` \| `instant-open`** | tooltip.tsx |

   *Source for all rows: `https://raw.githubusercontent.com/radix-ui/primitives/main/packages/react/<name>/src/<name>.tsx`,
   fetched 2026-09-28. Confidence: primary.*

   Consequence for a brand kit: **there is no single Radix `data-state` vocabulary.** Overlay-ish parts say
   `open`/`closed`; selection-ish parts say `active`/`inactive` or `checked`/`unchecked`; tooltip has a *third* value that
   encodes **how** it opened, not just whether. Adopting "the Radix way" without picking the vocabulary per slot is the
   obvious failure mode.

2. **`delayed-open` / `instant-open` is a genuinely transferable idea with no equivalent anywhere else in the five.**
   A brand can style "hover a second time" differently from "first hover" *without adding a prop*, because the
   distinction is in the attribute value. Radix derives it from `wasOpenDelayedRef` + a provider-level
   `isOpenDelayedRef`/`skipDelayDuration` (default 300ms, `delayDuration` default 700ms — `DEFAULT_DELAY_DURATION = 700`).

3. **Base UI's attribute names are mechanically derived, not hand-listed.** `getStateAttributesProps.ts` loops the
   component's internal `state` object and emits `data-${key.toLowerCase()}`; `true` → `''`, other truthy → `.toString()`,
   falsy → **attribute omitted entirely**. A per-component `stateAttributesMapping` can override any key.
   This means: *naming a new Base UI state key automatically names the CSS hook*, and it also means a `false` state
   produces **no attribute at all** — you style `[data-open]` and `[data-closed]` as presence selectors, not
   `[data-open="false"]`.
   Source: `https://raw.githubusercontent.com/mui/base-ui/master/packages/react/src/internals/getStateAttributesProps.ts`, 2026-09-28, primary.

### 1b. Which attribute name for "highlighted" — the libraries do not agree

| Library | Name | Encoding | Source |
|---|---|---|---|
| Radix | `data-highlighted` | `isFocused ? '' : undefined` | menu.tsx (`MenuItemImpl`) |
| Base UI | `data-highlighted` | presence | dialog.md, styling handbook |
| Ark UI | `data-highlighted` | presence (docs explicitly say "do not look for a value such as `true`") | ark-ui.com styling guide |
| Headless UI | **`data-focus`** | presence | headlessui.com/react/listbox |
| Reakit | *(none documented)* | — | — |

`focus` vs `highlighted` is a real fork. Headless UI's `data-focus` is genuinely focus, not hover — its docs state it
tells you "if the option is currently focused via the mouse **or keyboard**", i.e. it is a *virtual* focus
(`data-focus:bg-blue-100` in their own example). Radix/Base UI/Ark's `data-highlighted` is the ARIA-menu "current
descendant" concept, and Radix implements it by actually calling `item.focus({preventScroll:true})` on `pointermove`
and tracking `isFocused` state — deliberate, with a comment explaining that `mouseOver`/`mouseEnter` would not re-focus
when the mouse wiggles.

### 1c. `className`-as-a-function of state — only Base UI and Ark

- **Base UI**: `className` *and* `style` both accept `(state) => value`, resolved by `resolveClassName` / `resolveStyle`.
  Docs: `<Switch.Thumb className={(state) => (state.checked ? 'checked' : 'unchecked')} />`.
  Source: `https://base-ui.com/react/handbook/styling`, 2026-09-28, primary; implementation `useRenderElement.tsx`.
- **Ark UI**: no function form; `class`/`className` is a plain string and state is read off `data-*` (or via Panda's
  `_open` conditions). Source: `https://ark-ui.com/docs/guides/styling`, 2026-09-28, primary.
- **Radix**: `className` is a plain string; state is read off `data-*` only.
- **Headless UI**: neither. It uses **render props** — `className` is a string, and you pass a *function child*
  (`{({ focus, selected }) => ...}`) with `as={Fragment}` to compute classes yourself.
- **Reakit**: neither; props + `unstyled`/`unstable_system`.

**This is the most transferable mechanism in the whole angle for a StyleX-based kit** — see §7.

## 2. Slot & prop composition

| Library | Mechanism | Exact detail | Source |
|---|---|---|---|
| Radix | `asChild` on every part + `createSlot` / `Slottable` | `Primitive.button`/`div` render a default tag; `asChild` merges behaviour into *your* element instead. `Slottable` marks where a passed child lands (Tooltip uses it). | tooltip.tsx imports `createSlottable`; dialog.tsx uses `createSlot('DialogOverlay.RemoveScroll')` |
| Base UI | `render` prop, **two forms** | `render={<X/>}` → `mergeProps(props, render.props)` then `React.cloneElement(render, mergedProps)`. `render={(props, state) => <X {...props}/>} ` → called as a **plain function** (dev warning if the function name is PascalCase: "Base UI calls `render` as a plain function, which can break the Rules of Hooks"). Also auto-adds `type="button"` on a bare `button` and `alt=""` on a bare `img`. | `useRenderElement.tsx` |
| Ark UI | anatomy + `data-scope`/`data-part` | Zag's `parts.<name>.attrs` is spread into every prop-getter, so scope/part are emitted from the anatomy, not per-component. `@ark-ui/react/anatomy` exports the slot key list for Panda `defineSlotRecipe`. | `dialog.connect.ts`; ark-ui.com styling guide |
| Headless UI | `as` prop (`as={Fragment}`) + render props | `as` selects element **or component**; function children get the state object. | headlessui.com docs |
| Reakit | `as` prop + `unstyled` + `unstable_system` | Docs explicitly warn styled-components owns `as`, so you must use `forwardedAs` with Reakit. | reakit.io/docs/styling |

Base UI's `render` function form is the **one place in this landscape where the library documents its own footgun**, and
it is worth quoting to any team choosing a composition model: a PascalCase function passed to `render` breaks the Rules
of Hooks. `asChild` (Radix) and `as={Fragment}` + function child (Headless UI) do not have this class of bug.

## 3. Focus-management contract

### Radix — `FocusScope` (`packages/react/focus-scope/src/focus-scope.tsx`)

Props: `loop`, `trapped`, `branches`, `onMountAutoFocus`, `onUnmountAutoFocus`.

- **Open**: dispatches a **cancelable** `CustomEvent('focusScope.autoFocusOnMount')` on the container. If not prevented,
  focuses `focusFirst(removeLinks(getTabbableCandidates(container)), { select: true })`; if focus did not actually move,
  falls back to focusing the container itself.
- **Close**: `setTimeout(0)` (explicit comment: works around a React <17 unmount-focus bug), dispatches cancelable
  `CustomEvent('focusScope.autoFocusOnUnmount')`, and if not prevented focuses `previouslyFocusedElement ?? document.body`
  with `{ select: true }`.
- **Container** is always `tabIndex={-1}`.
- **Trap** = document-level `focusin` + `focusout` listeners + a `MutationObserver` on the container's subtree:
  - `focusin` outside → refocus last in-scope element.
  - `focusout` with `relatedTarget === null` is **deliberately ignored** (window blur, and Chrome removing the node —
    comment: refocusing a deleted element in Chrome "throws the CPU to 100%").
  - `MutationObserver` catches the focused node being removed (browser falls focus to `body`) and refocuses the container.
- **Branches**: portalled children of a modal layer register via `useFocusScopeBranch` so the trap does not reclaim focus
  from them. Motivated by issue #3423.

**Dialog, modal** (`dialog.tsx`): `trapFocus={context.open}`, `disableOutsidePointerEvents={context.open}`,
`onCloseAutoFocus` → `event.preventDefault(); context.triggerRef.current?.focus()`. Also `hideOthers(content)` from
`aria-hidden` ("better supported equivalent to setting `aria-modal`"), `onFocusOutside` is `preventDefault`ed so a trapped
`focusout` cannot trigger dismiss, and right-click (button 2, or button 0 + ctrl) is `preventDefault`ed so a right-click
does not close.

**Dialog, non-modal**: `trapFocus={false}`, `disableOutsidePointerEvents={false}`; on close it restores focus to the
trigger **only if no outside interaction already happened** (`hasInteractedOutsideRef`), and `onInteractOutside` is
prevented when the target is inside the trigger (otherwise it closes and immediately reopens). There is a Safari-specific
guard: a `focusin` outside is ignored if a `pointerdown` outside already fired.

**Menu** (`menu.tsx`): on open it `event.preventDefault()`s the default mount focus and explicitly focuses the *content
element* only, leaving `RovingFocusGroup`'s `onEntryFocus` in charge of focusing the first item — and that callback is
itself prevented unless `rootContext.isUsingKeyboardRef.current`. So **a mouse-opened menu does not move focus to an
item; a keyboard-opened one does.**

### Headless UI

- `Dialog` focuses **its own root element** on open by default; `Tab` cycles inside; everything outside is marked
  **`inert`**. Override with `autoFocus` on a Headless UI form control, or `data-autofocus` on any element.
- `open` still drives scroll-locking and focus trapping even when `static` is set.
- Source: `https://headlessui.com/react/dialog` (Managing initial focus), 2026-09-28, primary.

### Base UI

`Dialog.Popup` exposes `initialFocus` / `finalFocus` refs (visible in the docs' "focus on open/close" example). Exact trap
implementation not read from source — see Gaps.

### Ark UI

`dialog.connect.ts`: `getContentProps` sets `tabIndex: -1` and `aria-modal: prop("modal")`; the machine (`"open"` state)
drives the focus effect. Not read line-by-line — see Gaps.

### Reakit

No focus-trap story documented on reakit.io. Components are described as "pretty much stateless" with state passed as
props; `Tabbable` is an abstract component in the nav, not a documented trap contract.

**`FocusGroup` vs `RovingFocusGroup`:** `RovingFocusGroup` is the one that exists as a public package
(`@radix-ui/react-roving-focus`, `Root` / `Item`). There is **no public `FocusGroup` component** — "FocusGroup" in
Radix vocabulary is the *concept* of managing a set of managed focusable elements, implemented by the roving primitive.
Grep of the packages read this pass found no `focus-group` package. Marked as verified-negative for the packages read
(dialog, dismissable-layer, focus-scope, roving-focus, presence, menu, popper, popper, tabs, accordion, collapsible,
checkbox, switch, tooltip); a full `packages/react/*` listing was not enumerated — see Gaps.

## 5. Overlay: portal, z-index, dismissal, nesting

### Radix `DismissableLayer` (`dismissable-layer.tsx`)

- **Layer stack** = an insertion-ordered `Set` in a React context (`layers`, `layersWithOutsidePointerEventsDisabled`,
  `branches`, `dismissableSurfaces`). Order is **creation order**, and the file has an explicit comment that the
  "disable pointer events" effect is deliberately *not* merged with the registration effect, because a change to
  `disableOutsidePointerEvents` would otherwise remove-and-re-add the layer and break creation ordering.
- **Escape**: a single `keydown` listener on `ownerDocument` with **`capture: true`**, registered **only for
  `isHighestLayer`** (last in the set). So Escape always closes the top-most layer, never the whole stack.
  `onEscapeKeyDown` runs first; dismissal only proceeds if `event.defaultPrevented` is false, and it calls
  `event.preventDefault()` before `onDismiss()`.
- **Outside pointer events**: `disableOutsidePointerEvents` sets `document.body.style.pointerEvents = 'none'` (once, saving
  the original) and each layer gets an inline `pointerEvents: 'auto' | 'none'` based on
  `index >= highestLayerWithOutsidePointerEventsDisabledIndex`. The body value is restored when the last disabled layer
  unmounts **or when the prop flips to false while still mounted** (issue #3645 — a modal closing but still animating out
  used to leave `body { pointer-events: none }`).
- **Two opt-outs**: `onPointerDownOutside` (waits for the click so third parties can cancel), `onFocusOutside`, and their
  union `onInteractOutside` — all cancelable via `defaultPrevented`.
- **`DismissableLayerBranch`** (new) and **`useDismissableLayerSurface()`** (new, issue #3346) exist so that a dialog
  *overlay* counts as part of its own dismiss surface: a consumer calling `stopPropagation` on the overlay no longer
  prevents the dialog from closing.
- **Scroll lock** is not in this file — it is `react-remove-scroll` with `shards` including the content ref and any
  registered branch nodes (issue #3423).

### Radix `Presence` (`presence.tsx`) — the exit-animation mechanism

State machine: `mounted → (ANIMATION_OUT) → unmounted` … `mounted ↔ unmountSuspended` (delayed unmount during exit).

- There is **no `animationrun` event** and `animationstart` fires after `animation-delay`, so exit detection is done by
  **diffing `getComputedStyle(node).animationName`** across the `present` flip. If the current animation name is `none` or
  `display: none`, it unmounts instantly.
- Listens for `animationstart`, `animationend`, **and `animationcancel`** (interrupting an enter with an exit fires
  `animationcancel`; treated as end, guarded by a `CSS.escape` name comparison).
- Sets `node.style.animationFillMode = 'forwards'` on exit-end and restores it in a `setTimeout`, because with React 18
  concurrency the update lands a frame late and the removal otherwise flashes (PR #1849). A `requestAnimationFrame`
  restore was tried and still flashed.
- Passing a **function child** forces mount and hands you `{ present }`; that is how Collapsible/Tabs/Accordion measure
  dimensions before unmounting.
- `Collapsible` is the reference consumer: it zeroes `transitionDuration`/`animationName`, reads `getBoundingClientRect()`,
  publishes `--radix-collapsible-content-height` / `-width`, then restores — so a `grid-template-rows: 0fr → 1fr`
  collapse animates without JS layout math.

### Radix z-index — **there is no z-index scale**

Verified: no `zIndex` is set in dialog.tsx, popover.tsx, menu.tsx, popper.tsx, dismissable-layer.tsx or focus-scope.tsx.
The only z-index logic is in `popper.tsx`: the wrapper div **reads the computed z-index off the content and re-applies it
to the wrapper**, because Floating UI's transform is applied to the wrapper and the content's own stacking would be lost.
Radix's own styling guide states the consumer owns functional styles ("by default a Dialog Overlay won't cover the entire
viewport"). So a Radix app's z-index discipline is 100% shadcn/ui's `z-50` convention, not the library's.

### Ark UI — the only library in scope with a documented z-index model

Verbatim from the Ark styling guide: *"Ark UI does not prescribe a global z-index scale. You decide the base z-index
value for overlays, and Ark exposes Zag's `--layer-index` variable to keep stacked overlays in the right order."*
`--layer-index` is **a zero-based index for open dismissible layers, to be used as an offset, not as the full z-index**:

```css
[data-scope='dialog'][data-part='content']   { z-index: calc(var(--z-index-overlay) + var(--layer-index, 0)); }
[data-scope='dialog'][data-part='positioner']{ z-index: var(--z-index, var(--z-index-overlay)); }
[data-scope='dialog'][data-part='backdrop']  { z-index: calc(var(--z-index, var(--z-index-overlay)) - 1); }
```

The guide explicitly warns against `z-index: var(--layer-index)` alone ("produces values like `0`, `1`, `2`, which can
appear below headers, sidebars"). It also ships `data-nested`, `data-has-nested`, `--nested-layer-count`, and warns that
`transform`/`filter`/`opacity`/`contain`/`isolation`/`perspective` create stacking contexts that trap inline overlays.

### Base UI — stacking is delegated to the app root

Quick start instructs: wrap the app in `.root { isolation: isolate; }` so portalled popups always sit above page content
and "any `z-index` property in your styles won't interfere with them". No z-index token, no layer index, documented
anywhere in the handbook.

### Headless UI

`portal` prop (default `false`) on listbox/menu/combobox/popover; docs state `portal` is **automatically set to `true` when
`anchor` is set**. z-index is the consumer's (`className="relative z-50"` appears in the Dialog docs' own examples).

### Headless UI `anchor` — CSS-native positioning, no JS placement props

| Key | Default | CSS variable equivalent |
|---|---|---|
| `anchor.to` | `bottom` | — (`top`/`right`/`bottom`/`left` combined with `start`/`end`, or `selection`) |
| `anchor.gap` | `0` | `--anchor-gap` |
| `anchor.offset` | `0` | `--anchor-offset` |
| `anchor.padding` | `0` | `--anchor-padding` |

Source: `https://headlessui.com/react/listbox` (Component API table), 2026-09-28, primary. Example:
`<ListboxOptions anchor="bottom start" className="[--anchor-gap:4px] sm:[--anchor-gap:8px]">`.

### Radix positioning CSS variables (`popper.tsx`)

`--radix-popper-available-width`, `--radix-popper-available-height`, `--radix-popper-anchor-width`,
`--radix-popper-anchor-height`, `--radix-popper-transform-origin`. Wrapper carries
`data-radix-popper-content-wrapper=""` and `transform: translate(0, -200%)` while unpositioned. Animation is forced to
`none` until `isPositioned`, "so that users' animations don't kick in too early from the wrong sides".
Collapsible adds `--radix-collapsible-content-height` / `-width`.

### Base UI positioning CSS variables (docs)

`--positioner-width`, `--positioner-height`, `--available-width`, `--available-height`, `--anchor-width`,
`--anchor-height`, `--transform-origin`, `--popup-width`, `--popup-height`, `--anchor-gap`.

> **Looking for Reakit's successor? [Visit Ariakit](https://ariakit.org/)**

| Successor | Ariakit, at `ariakit.org` → `ariakit.com` (v0.4.40), published by the same author | `https://ariakit.org/`, `https://ariakit.com/`, 2026-09-28, primary |
| Docs still fully published | all 16 components + 8 abstract components + 7 guides live | `https://reakit.io/docs/`, 2026-09-28, primary |

**Verdict:** Reakit is **superseded and in maintenance-only-or-frozen state**, but the owner never used the words
"deprecated" or "unmaintained". The repo was **renamed**, not archived (`archived: false`, and Ariakit itself is
actively pushed to). Reakit is cited as prior art by both Zag and Ariakit. Treat as **historical reference, not
adoptable** — the mechanisms are documented and readable, but nothing ships behind it.

**Why it is still in scope for this harvest:** Reakit is the *origin* of the composition pattern (`as` prop, `unstyled`,
`use*State` hooks, `Portal`/`Tabbable`/`Composite` as abstract components) that Ariakit reworked into the `data-*` model.
Its own styling guide documents **no `data-*` state contract at all** — the only styling options listed are *unstyled
(default)*, *inline styles*, *CSS Modules*, *CSS in JS*. That absence is the finding: Reakit's answer to "how do I style
this state" was "you already have the prop; branch on it yourself."

## 7. Mechanism recommendations mapped to Astryx artifacts (PROPOSALS — nothing approved)

Every item names a concrete artifact. No new hex/font/radius asserted. Any **new token name** is flagged
`NEEDS-HUMAN-APPROVAL` because the brief forbids asserting new token names.

### ADOPT-1 — Base UI's `className`/`style`-as-a-function-of-state (the only mechanism that survives StyleX)

**Why this one first:** Radix's and Headless UI's state styling is *entirely* `data-*` attribute selectors, and the
Astryx kit styles with **StyleX** (`stylex.create` + `xstyle` per the brief's baseline). StyleX's documented API is
pseudo-selectors + media queries, not arbitrary attribute selectors. I have **not** verified StyleX's selector set against
its own docs in this worker — flagged as a gap, and it must be verified before any recommendation rests on it. But the
mechanism that does not care is Base UI's: compute the variant in JS from a state object and hand StyleX a different
`xstyle`. `getStateAttributesProps.ts` is the reference implementation — 20 lines, one loop, no per-component list.

| Artifact | Change proposed |
|---|---|
| `astryx-theme.ts` | each interactive style object gains a state-parameterised variant, mirroring `getStateAttributesProps`'s "one loop over the state object" shape rather than per-component hand-written variants |
| Any Astryx component slot that currently branches state in the template | move the branch into the style layer |

### ADOPT-2 — Pick the state vocabulary *per slot* and write it down, using Radix as the evidence

`data-state` is not one vocabulary in the wild (see §1a). Recommendation: Astryx defines **two** vocabularies, not one:
- **disclosure/overlay slots** → `open` | `closed` (Radix Dialog/Popover/Collapsible agreement)
- **selection slots** → `checked` | `unchecked` (+ `indeterminate` if any tri-state control ships) (Radix Checkbox agreement)
- plus a **third optional value on tooltip-like slots** for "opened without delay" — Radix's `delayed-open` /
  `instant-open` (tooltip.tsx). This costs one attribute value and one provider flag, and gives the brand a fast-tooltip
  path with no new prop and no new token.

Artifact: the state-attribute contract belongs in the Astryx component theme module, not in `tokens.css` (it is behaviour,
not colour). `NEEDS-HUMAN-APPROVAL: the exact state-vocabulary table and where it is published (SKILL.md vs BRAND.md).`

### ADOPT-3 — Ark UI's one-base-plus-`--layer-index` overlay model

Radix has no z-index model at all; Base UI delegates to `isolation: isolate`; Headless UI hands it to the consumer. Ark is
the only one that solves *nested* layers, and its solution is one base value plus a zero-based counter — which is exactly
the shape a dark-only brand kit with a fixed chrome/content hierarchy wants.

Artifact: `tokens.css` (the layer owns scrollbars and global chrome) + `astryx-theme.ts`.
`NEEDS-HUMAN-APPROVAL: the base overlay token name and its value.`

### ADOPT-4 — `data-starting-style` / `data-ending-style` (Base UI) as the exit-animation contract

The brief records that Astryx 0.3.0 ships **no exit-animation helper**. Two competing mechanisms exist:
- **Radix `Presence`**: JS. Diff `getComputedStyle().animationName`, hold the node in `unmountSuspended`, listen for
  `animationend`/`animationcancel`, force `animation-fill-mode: forwards`, restore in a `setTimeout`.
- **Base UI**: CSS-only. The element stays mounted and the library flips two presence attributes; CSS owns the timing.
  Docs use it uniformly: `transition … data-starting-style:opacity-0 data-ending-style:opacity-0`, including a
  *different duration for exit* (`data-ending-style:duration-[350ms]`) — which Radix cannot express declaratively.

The Base UI one is the cheaper fit for a kit that already has 9 duration tokens and a single easing. Radix's is more
robust when you need to measure (Collapsible's height/width publication). Note Radix's own `--radix-collapsible-content-height`
pattern is the only primitive in this landscape that makes a height animation work with zero JS in the consumer.

### REJECT-1 — Reakit's prop-only state model

20+ boolean props, no `data-*`, styling by branching in the template. It is also the reason Ariakit exists. Reject.

### REJECT-2 — Base UI's function form of `render`

`render={(props, state) => ...}` is called as a **plain function**, and the library ships a dev warning precisely because
passing a component (`render={Component}`) breaks the Rules of Hooks during reconciliation. Prefer Radix's `asChild` or
Headless UI's `as={Fragment}` + function child: neither can be handed a component by accident. (Base UI's **element**
form is fine and is what `asChild` is.)

### REJECT-3 — Headless UI's render-prop-only styling

Headless UI has no `className`-as-a-function. To compute a class from state you must switch the subtree to
`as={Fragment}` and write a function child. That forces every styled element to become a wrapper you hand-write.
Adopt its `data-*` names (`data-open`, `data-focus` if preferred) if wanted; reject the render-prop requirement.

## 9. Counter-angle — documented failure modes in the source itself

Radix's own source files cite issue numbers for correctness bugs in exactly the layer/focus machinery this angle
recommends borrowing. These are the maintainers' own acknowledgements, found in comments, not third-party bug reports:

| Issue | What broke | Source comment |
|---|---|---|
| #3423 | Nested portalled layers (a non-modal Popover inside a Dialog) were treated as outside the Dialog for focus trapping and scroll locking | dialog.tsx, popover.tsx, focus-scope.tsx, menu.tsx — this is why `branches` / `useFocusScopeBranch` / `RemoveScroll` `shards` exist |
| #3346 | A consumer calling `stopPropagation` on the Dialog overlay prevented the dialog from closing | dialog.tsx → `useDismissableLayerSurface()` |
| #3645 | `body { pointer-events: none }` was left behind when a modal closed but stayed mounted during its exit animation | dismissable-layer.tsx |
| #4014 | `useEffectEvent` returns a stale closure inside `forwardRef` on React 19.2.x, so escape handlers saw mount-time props. Worked around with `useCallbackRef`, with an explicit "we should revert this when the fix lands" comment referencing `facebook/react#34831`. | dismissable-layer.tsx |
| #3077 | `RovingFocusGroup` rendered `tabIndex={-1}` until items registered in an effect, so `FocusScope` skipped the group when auto-focusing on open. Fixed by registering in a `useLayoutEffect` **after hydration** and a passive effect before it. | roving-focus-group.tsx |
| #3232 / #3600 | Portalled focusable descendants bubble keys into MenuItem/TabsTrigger and get swallowed; Tab loses focus to `document` when the active tab is removed. Both fixed by `event.target !== event.currentTarget` guards. | menu.tsx, tabs.tsx |
| #3664 | A consumer callback-ref whose identity changed each commit caused `Presence` to loop with "Maximum update depth exceeded" on React 19. | presence.tsx |
| #1634 | Reading the live `CSSStyleDeclaration` in a passive effect forced a synchronous style recalc; fixed by capturing `animationName` during the layout phase / ref callback. | presence.tsx |

**Read:** the focus/layer stack is genuinely subtle and every one of these was found after release. Anyone adopting
`DismissableLayer` + `FocusScope` + `RovingFocusGroup` as a pattern inherits the pattern *and* its eight bug classes.
**Headless UI's changelog is the same story from the other side** — 2.2.x is almost entirely focus and dismissal fixes:
"Fix restoring focus to correct element when closing `Dialog`", "Fix outside click in nested portalled `Popover`
components", "Ensure sibling `Dialog` components are scrollable on mobile", "Don't activate hovered items while using
the keyboard", "Fix closing `Menu` when other `Menu` is opened".

## Conflicting evidence

1. **"Reakit is deprecated / unmaintained" (widely reported) vs. the owner's actual words.** The owner's own statement is
   **"Looking for Reakit's successor?"** — a supersession notice, not a deprecation notice. **Resolution: the owner
   wins on wording.** Reakit is superseded and its repo was renamed to `ariakit/ariakit`; `archived` is `false` and
   Ariakit is actively pushed to. The correct characterisation for the report is **"superseded; not deprecated in the
   owner's language; nothing ships behind it"** — not "unmaintained", and never "archived".

2. **Radix `data-state` is presented in its own styling guide as if it were one thing** ("when components are stateful,
   their state will be exposed in a `data-state` attribute… e.g. `data-state="open"`"), while the source shows four
   different value vocabularies. **Resolution: source wins.** The guide's example is `open`, but a consumer who
   generalises from it will write `[data-state="checked"]` against a Tabs trigger and get nothing. The guide also
   explicitly defers to each component's own "Data attributes" table, so there is no actual contradiction — only a
   summary page that under-specifies.

3. **`data-focus` (Headless UI) vs `data-highlighted` (the other three).** Not a contradiction — different concepts
   (real/virtual DOM focus vs. ARIA active descendant). But it is a genuine fork in the vocabulary, and a kit that
   copies both Radix's and Headless UI's names into one component set will have two words for adjacent ideas.

4. **Ark UI's positioning/z-index guidance vs. Base UI's `isolation: isolate`.** Two defensible answers to "how do portalled
   overlays stack": derive the order from the layer registry (Ark), or escape the whole problem by isolating the app root
   (Base UI). They are not mutually exclusive; the report should present Ark's as strictly more informative because it
   survives *nested* layers, which `isolation: isolate` alone does not order.

## Gaps

1. **StyleX selector support is the load-bearing unknown for ADOPT-1 and I did not verify it.** Every recommendation about
   transferring Radix/Headless UI's `data-*` model into the Astryx kit hinges on whether StyleX supports arbitrary
   attribute selectors. I asserted StyleX's API from the brief's baseline, not from StyleX's own docs. **Must be checked
   against the StyleX documentation before ADOPT-1 is written into the report as a recommendation.** If StyleX does
   support attribute selectors, ADOPT-1 weakens to "nice" and the `data-*` model becomes viable; if it does not,
   ADOPT-1 is the *only* viable mechanism and the report should say so loudly.

2. **Base UI's focus trap was not read from source.** Only the `initialFocus` / `finalFocus` props were seen, in a docs
   example. The actual trap/restore implementation (which package, what inert strategy, whether it is `focus-trap`-style
   or a MutationObserver) is unverified.

3. **Ark UI's per-component data-attribute tables were not enumerated.** Only the Dialog machine's `connect.ts` was read;
   `data-highlighted` / `data-disabled` / `data-checked` come from the docs' styling guide prose, not from a machine
   source file. A component-by-component Ark table would need either the anatomy docs or each `*.connect.ts`.

4. **Radix `Select` was not read.** `data-highlighted`, `data-placeholder`, `data-state` on the trigger, and Select's
   typeahead are all documented on radix-ui.com but the source was not opened. Given that `data-state="checked"` on
   Select items is the most-copied snippet in the ecosystem, this is worth one more read.

5. **Verified-negative caveat on "no public `FocusGroup` component."** No `focus-group` package appeared in the 13 Radix
   files read, but `packages/react/*` was never enumerated. Treat as "not observed", not "does not exist".

6. **Reakit's last publish date was not obtained.** The npm full document is 8439 lines and was truncated at line 300; the
   `time` map sits at the end. `dist-tags` were captured (`latest 1.3.11`) but the release date of 1.3.11 is
   **unverified** and must not be stated as a number in the report without the abbreviated-metadata fetch.

7. **No a11y audit of any of the five was performed.** This angle covers *mechanisms*; whether the mechanisms are
   *correct* in practice needs the counter-angle worker's issue-tracker sweep, not source reading.

8. **Tooltip was the only component examined from the "truncation / tooltip / empty-state" axis.** Headless UI's
   `Description`/`Field` (form-text plumbing) and Ark's `TagsInput`/`Tree` were not read.
