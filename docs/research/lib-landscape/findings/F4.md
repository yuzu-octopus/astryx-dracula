**Transfer to a token-driven `Table` slot**

- A1/A2 → **adopt the *shape*, reject the name.** `meta` is a good pattern (a typed bag of app-supplied functions reachable from any cell), but Astryx's Table is StyleX, not headless. The transferable piece is: *one typed escape hatch on the Table instance for per-cell application functions*, not a `getRowStyle` prop.
- A6 `getIsSomeColumnsVisible` → the "partial" state. Astryx Table has no column-visibility control today; if one ships, a tri-state (all / some / none) is the correct primitive, and it maps to a `data-*` attribute the token layer can style.
- A8 `flexRender` + `getVisibleCells()` → the cell-render contract. Already implicit in Astryx's `renderCell`; the transferable idea is that **visibility is resolved per row, not per column**, so a hidden column costs nothing at render time.
- **REJECT: a TanStack-style density model.** A3 proves there isn't one. There is no mechanism to copy; inventing a `density="compact|comfortable"` prop on Astryx Table would be kit-invented and needs human approval of the prop name and the spacing values. `NEEDS-HUMAN-APPROVAL: Table density prop name + the padding tokens it maps to (core spacing steps 0–12 are the only candidates; no new values required if the two modes map to existing step indices)`.
- A9 controlled/uncontrolled pairs → if Astryx Table ever ships column pinning, the `reset*(defaultState?)` boolean flag is a small, real ergonomic win (reset-to-blank vs reset-to-initial). Cheap to copy, no token needed.

**Transfer to `shared/chart-hues` / `shared/revenue-chart`**

- B2's **text-inheritance post-pass is the single most transferable thing in this whole angle.** One root text style propagates to 9 consumer sites. Astryx's hand-rolled chart modules repeat the fill decision per scene (this is the finding ColorMotion raised independently). The mechanism: declare the text fill **once** per chart module and let every label/tick/legend read it. Zero new tokens, zero new hexes — it is a code-shape transfer.
- B5 is a **REJECT-side warning for `shared/*` chart work**: it is the exact failure mode of a token-driven chart. Any Astryx chart helper that wants to *derive* a colour (darken a mark, fade a series) must receive a resolved hex, not `var(--dracula-x)`. StyleX builds to static CSS, so this is largely a non-issue for Astryx — record it as the reason charts must derive at build time, not runtime.
- B3/B4 → Nivo's 11 hardcoded hexes and 4 font sizes are exactly the anti-pattern `shared/chart-hues` exists to prevent. - B1's **throwing `useTheme()`** is a good pattern for a token system: a missing theme is a hard error, not a silent default. Astryx's `xstyle`/StyleX model fails differently (missing class = unstyled), so this does not transfer — but the *intent* (loud failure over silent fallback) is worth noting.
- **Dark mode:** Nivo has no mode concept at all. There is no `prefers-color-scheme` fork, no `light-dark()`, no mode toggle — you pass a different theme object. This **survives dark-only trivially**: our `pin()`-every-tuple model is just "one theme object, always the same one." Nothing to invert, nothing to reject.

**Transfer to `shared/chart-hues` / `shared/revenue-chart` / `shared/sparkline`**

- **C2 is the headline adopt.** Astryx's `shared/chart-hues` is a positional array. Recharts solves the same problem with a **stable key→slot assignment by sorted `dataKey`**, independent of render order, with legend and tooltip inheriting the assignment. The transferable rule, stated for Astryx: *a series' colour must be a function of the series' identity, never of its position in the JSX.* Zero new tokens, zero new hexes. It fixes the class of bug where reordering children silently recolours a chart.
- C2's honest caveat must ship with the rule: "adding or removing a graphical item **can** change the assignment of the remaining items." Recharts solves this by sorting the *set of keys*, so the same key is stable as long as the same set exists. Astryx has no such guarantee today.
- **C5 is the best transferable mechanism in this angle for hand-rolled SVG.** Astryx's charts are hand-rolled and currently have no declared layer order. `DefaultZIndexes` is a *named constant table with one sentence of rationale per layer* — the name is the documentation. - **C6 is a REJECT-shaped warning.** Recharts routes the tooltip through an ungoverned portal that explicitly opts out of the z-index system. Astryx's tooltip tier is an open question at the grill; the transferable lesson is that a chart tooltip that escapes the chart's own stacking context cannot be themed by a token layer that assumes it does not.
- **C10's naming inconsistency is a concrete argument for a `shared/chart-legend.tsx`.** The `labelStyle`-means-two-things hazard is exactly what a single shared module with a fixed internal prop shape eliminates.
- C8's axis defaults (`tickSize 6`, `tickMargin 2`, `minTickGap 5`) are numbers to compare against, not adopt. `NEEDS-HUMAN-APPROVAL` if any are to be adopted; no values proposed.

**Correction to the reject argument, made because D8–D11 are stronger than the doc-based version**

- D8 supersedes the secondary claim: Tremor's Table has no state mechanism **at all** — not even a documented one. D5's `ui-selected:` variant is a *safelist entry*, i.e. Tremor anticipates consumers adding selection classes, but the library itself never applies one. So the honest statement is: **Tremor's own Table does not demonstrate the `data-selected` convention; its documentation's safelist merely reserves room for it.** The convention in D5 is still worth aligning on (it is a documented, first-class variant name), but the justification is now "Tremor reserves the name" rather than "Tremor uses it."
- **D9 is a new finding relevant to the brand's dense tables.** `whitespace-nowrap` as a shipped default means a Tremor table cell's overflow behaviour is opt-out, not opt-in. Astryx's dense templates need the opposite default posture. Recording it as evidence that "no built-in truncation policy" is the norm even in a chart-first dashboard kit.
- **D10 upgrades the D3 rejection from "inconvenient" to "structurally incompatible."** A library that ships no CSS and emits only class names has delegated its entire visual contract to a third-party build tool. A brand kit whose contract is `theme.css` + `tokens.css` cannot delegate anything. This is the single strongest reject argument in the data/layout tier.

**Why Tremor is a REJECT candidate — mechanism-level, not taste**

1. **D10 + D2 are the hard blocker for a zero-dep StyleX kit.** The token system is not a token system; it is a block of JavaScript that must be pasted into a third-party build tool's config, in that tool's units (`rem`, arbitrary Tailwind shade indices). And the library ships **no CSS at all** — it emits class names whose bodies the consumer's Tailwind build must generate. A brand kit that publishes `theme.css` + `tokens.css` as its contract cannot delegate its palette *or its rule bodies* to a Tailwind config. The mechanism does not survive translation.
2. **D3 is the correctness form of the same argument.** A dynamic-class safelist means the theme is *build-time-coupled to class-name generation*. Astryx's `tokens.css` is a full unlayered mirror of `theme.css` — a published contract with zero build coupling. Tremor requires a restart on every palette change and silently drops colours that were not enumerated. Same defect class as D10, seen from the config side.
3. **D5 is worth aligning on, in name only.** `ui-selected:` / `data-[selected]:` is a reserved, documented variant in Tremor's own safelist — and D8 shows the library's Table never applies one, so the convention is a *contract with the consumer*, not an implementation. The separation it encodes is right: **`data-selected` as a styling hook, `aria-selected` as the accessibility state, kept distinct.** `NEEDS-HUMAN-APPROVAL: whether the exact attribute name `data-selected` is the one to standardise on across the kit's row-selection / chart-legend surfaces, or whether an existing Astryx attribute name already covers it.`
4. **D4 is the dark-mode verdict.** `prefers-color-scheme` as the *default* is precisely what the brief lists as settled-and-closed. Tremor also needs a **parallel token tree** (`dark-tremor-*`, 22 more names) where Astryx pins every tuple to one dark hex. Tremor's model would require Astryx to ship a light tree it does not want.
5. **D6 removes licensing as a reason to reject — licensing is clean.** Apache-2.0 for the package, MIT for the blocks, no current purchase. The rejection is structural (D10 + D2 + D3 + D4), not legal.
6. **D11 is the precedent worth recording.** Tremor is the clearest existing example of a kit that chose "re-skin a chart library through Tailwind classes" and paid for it with a safelist, a build restart, and a two-tree palette. Astryx has made the opposite bet — hand-rolled SVG plus `shared/chart-hues`. D11 is the strongest available evidence that the bet is the right one, because it shows what the alternative costs.

**Transfer vs Astryx's kanban/board templates**

- **F1's capability-descriptor pattern (`supports: [...]` vs `type: ...`) is the adopt.** It makes drop-target compatibility **data, not code** — a kanban column declares what it accepts, a card declares what it can go to, and the drop handler is one `includes` test instead of a switch over column ids. Applies directly to `templates/kanban-board.tsx`. Zero new tokens.
- **F4 is a free, high-value a11y rule** and it is stated as doctrine by the library, not inferred. Any board template that announces a position should say "position 2 of 5", not "index 1". No code change to the kit's tokens; a copy rule for the board templates.
- **F3 is a REJECT-shaped precedent for the brand's a11y posture.** dnd-kit ships English-only instructions "due to bundle size concerns" and treats the announcement strings as *consumer-owned*. Astryx's brand kit owns its own a11y convention (see the `role="img"` + unique-label discipline already noted elsewhere in this wave) — that is a different, stricter posture, and it means dnd-kit's default-and-override model is a floor, not a ceiling.
- F2's `aria-roledescription = "draggable"` is a concrete precedent for **adding a `data-*`-adjacent ARIA roledescription to Astryx board cards** so a screen reader announces "draggable card" rather than "button". Cheap, no token.
- **F5's 25 px arrow step is a number to reject.** It is documented as an arbitrary default. Astryx's board templates have no keyboard-move affordance today; if one is added, the step must be derived from the card height, not copied. `NEEDS-HUMAN-APPROVAL: keyboard-move step for board templates — no value proposed.`
- **E1 + F6 together argue against a dependency here too**, consistent with the zero-dep constraint: dnd-kit's value is ~10 kb of sensors + collision detection, and the transferable parts (F1, F4) are *conventions*, not code.
