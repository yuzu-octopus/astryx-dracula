# F0 — Astryx core 0.3.0 baseline (the thing to beat)

Method: read-only inspection of `node_modules/@astryxdesign/core` 0.3.0 + `bunx astryx docs <topic>` + `bunx astryx component <Name>`. No edits. Fetch date 2026-09-28. All rows confidence **primary** (first-party source in the installed package).

Why this file exists: acceptance requires "5 patterns where a third party does something **measurably better than core 0.3.0**". You cannot score that without pinning the baseline. Every "better than" claim in F1–F6 is measured against this file.

## Gaps found in core (the openings a library can beat)

### G1 — NO `data-*` STATE HOOKS IN THE *THEME API* (and, originally believed, in the components — corrected below). Confidence: primary.

`grep -rho 'data-[a-z-]*' dist --include=*.js | sort | uniq -c` returns `data-testid` (275), `data-theme` (29), `data-astryx-token` (21), `data-autofocus` (15), `data-avatar-item` (13), `data-toast-id` (8), `data-resizing` (8), `data-column-key` (6)… and **zero occurrences of `data-state` in the source text**. The *theme-API* state-styling surface is instead:
- internal StyleX pseudo-class rules, and
- theme-level `components: { button: { 'variant:secondary': {...} } }` where keys are **`prop:value` only** — `src/theme/defineTheme.ts` `ComponentStyleMap` doc comment enumerates `base`, `prop:value`, `prop:value+prop:value`.
- `StyleOverrides` accepts pseudo-class keys starting with `:` only — "Supported pseudo-classes include `:hover`, `:focus-visible`, `:active`, `:checked`, `:disabled`, etc." No `[aria-expanded]`, no `[data-state]` selector syntax anywhere in `defineTheme.ts` (grep for `aria-expanded` / `[aria-` / `[data-state` returns nothing).

**CORRECTION to G1, added 2026-09-28 after further measurement — this supersedes the headline of G1.**

G1's claim that core emits no `data-*` state attributes came from a **source-text** grep. That measured the wrong thing:

- `src/utils/themeProps.ts` is a **general `data-*` mechanism**. It builds the `astryx-*` class string *and* reflects visual props as data attributes, converting camelCase keys **at runtime** via `toDataAttributeName(prop)` = `prop.replace(/([a-z0-9])([A-Z])/g, '$1-$2').toLowerCase()`. **Because the attribute names are constructed, a literal grep for `data-state` returns 0 even when it is emitted.**
- Its own docblock states the intent: props are reflected as data attributes "so consumers target stable data-attribute selectors rather than collision-prone bare class names," citing `data-variant`, `data-size`, `data-level`.
- **270 call sites across ~80 components** (`grep -rn "themeProps(" src --include=*.tsx | grep -v '\.test\.'` = 270 call sites; component set enumerated).
- **7 of them pass a `state` key**, all emitting `expanded | collapsed`: `DateInput.tsx:679`, `DateRangeInput.tsx:585`, `Selector.tsx:1296`, `ComplexSelector.tsx:387`, `MultiSelector.tsx:1579`, `TreeListItem.tsx:447` and `:458`.

**Corrected form of G1:** the mechanism exists, is first-class and is widely used; `state` is passed at 7 of 270 sites. The gap is *under-use of an existing contract*, not absence of one. The `DateInput.tsx:677` comment reading "Reflects the popover's open/closed state as a `data-state` attribute" is **accurate**, not a stale comment.

**Method note, and it is the generalisable part:** any census of emitted attributes must be taken from the **rendered DOM or the emitting function**, never from literal source text. A runtime-constructed name is invisible to grep by construction.

**Also corrected: `data-custom` is test-only.** All occurrences are in `*.test.tsx` fixtures (`Breadcrumbs`, `Chat*`, `Collapsible`, `FieldStatus`, `Link`, `Markdown`, `MobileNav`, `SideNav`, `TabList`, `TopNav`); `grep -rln 'data-custom' src | grep -v '\.test\.'` returns **zero**. It is not a shipped prop.

**Original conclusion, now superseded by the correction above but retained for the record:** "a consumer cannot theme a component by ARIA or data state through the theme API, and core does not emit a state attribute for external CSS to hook." The **second half is wrong** — `themeProps` emits `data-state` at 7 sites. The **first half is right and still the actionable gap**: `defineTheme`'s `StyleOverrides` accepts only `:`-prefixed pseudo-classes, so a *token* cannot be authored against `[data-state]`. A brand override of that kind must go in unlayered `tokens.css` (see G10), which is precisely where the unlayered tail lives.

### G2 — NO z-index scale. Confidence: primary.
`grep -rn 'zIndex' src dist` → only bare literals: `zIndex: 1` (Thumbnail ×2, SideNav, Calendar, ChatComposer ×2, ChatLayout ×2, ChatDictationButton, ChatComposerDrawer, CodeBlock, CheckboxInput, Slider, Lightbox ×2), `zIndex: 0`, `zIndex: 2` (ChatComposer), and one outlier **`src/Toast/ToastViewport.tsx:28` → `zIndex: 500`**. No `--z-*` token exists in `tokens.stylex.ts` (grep for `--z-` → nothing). So overlay stacking is ad-hoc magic numbers, not a token scale.

### G3 — Overlay mechanics are already modern (do NOT let a library "improve" this). Confidence: primary.

Core is ahead of the 2020-era library baseline on overlays:
- Positioning uses **native CSS anchor positioning**: `src/Layer/useLayer.tsx:28` imports `addAnchorName`/`removeAnchorName`; `:548-550` sets `positionAnchor: anchorId`. No Floating UI, no JS measurement loop.
- Toasts promote to the **native top layer** via `popover="manual"` + `el.showPopover()` — `src/Toast/ToastViewport.tsx:364,431`, with the comment "popover='manual' promotes to the top layer (above dialogs)".
- Light-dismiss is delegated to the platform: `src/Typeahead/BaseTypeahead.tsx:361,402,604` and `src/Popover/usePopover.tsx:120` all discuss native `popover="auto"` light-dismiss semantics rather than reimplementing outside-click.
- Theme reaches portals by writing `data-astryx-theme` onto portal/fallback viewports — `src/Theme.tsx:212`, `src/Toast/useToast.tsx:26` ("for the theme's @scope'd CSS to reach it").

**Implication: Floating UI / Radix DismissableLayer / react-remove-scroll should be REJECT candidates for the overlay slot — core already has the platform-native equivalent, and the brand is "motion answers action", not "more JS".**

### G10 — The brand's only escape hatch is "unlayered", not "more specific". Confidence: primary.
`theme.css:9,80,731` — generated component CSS is `@layer astryx-theme { @scope ([data-astryx-theme="astryx-dracula"]) to ([data-astryx-theme]) { … } }`, i.e. **doubly** constrained (cascade layer AND `@scope`). `tokens.css:39-41` declares its `:root` block "Unlayered by design so it beats core layers; zero !important anywhere." `grep -n '@layer' tokens.css` returns **nothing** — the file has no layer at all.
Consequence, and it governs every recommendation in this report: a brand override that must win over core **cannot** be expressed as a more specific selector inside the theme, because the theme's selectors are already `@scope`d to a data-attribute boundary. It must be an **unlayered** rule in `tokens.css`. So "state styling by attribute" (G1) and "a z-index scale" (G2) cannot land in `defineTheme({components})` at all as things stand — they are `tokens.css` work, and any proposal that says otherwise is wrong about the cascade.

### G11 — The dark-only invariant is REAL and measured, and the obvious parser for it is WRONG. Confidence: primary.
Independently measured by CoreInvertedPairAudit (peer slice, theme/tokens/gates) in `theme.css`:
- `theme.css` contains **167 `light-dark()` tuples, 0 truly asymmetric** — i.e. every `pin(hex)` produced a genuinely equal pair. The dark-only claim is a measured property of the build, not an assertion in prose.
- `tokens.css` contains **0 `light-dark()` tuples** — it is frozen single values, as its header says.

**The trap, because it is load-bearing for any future gate on this invariant:** the natural regex `/light-dark\(\s*([^,]+?)\s*,\s*([^)]+?)\s*\)/` splits argument 2 on its first `)`. Our 45 sequential-ramp tokens are `hsl(264.71 89.47% 28%)`-shaped, so the parser truncates at the inner paren and reports **45 false positives** — every ramp token reads as asymmetric when it is identical. A gate written that way ships red on day one, and a red-by-design gate gets disabled within a week and then protects nothing, which is worse than no gate because it reads as coverage. Correct shape: walk from `light-dark(` tracking paren depth, split on commas only at depth 1, terminate on the matching `)`. A tuple whose arity is not 2 is malformed and should also fail.

### G4 — Reduced motion is per-component, not global. Confidence: primary.
`grep -rn 'prefers-reduced-motion' src` → ~14 component files each hand-roll `'@media (prefers-reduced-motion: reduce)': '0s' | 'none' | '0ms' | '0.01ms'`. There is no global motion-token kill switch in the theme. (This is the same finding Main routed to CoreInvertedPairAudit for a `tokens.css` unlayered block — a brand-layer fix for a core-layer gap.)

### G5 — One easing, no transition-property tokens. Confidence: primary.
`grep -rhoE 'transition(Property|Duration|TimingFunction)?: [^,]*' src` → `transitionTimingFunction: easeVars['--ease-standard']` ×104, `transitionDuration: durationVars['--duration-fast']` ×51, `--duration-medium` ×9, but 6 sites use a raw `'150ms'` and 2 use a raw `'ease-out'`. `--ease-standard` is a single curve used for everything — no enter/exit distinction, no spring/emphasized curve, and `transitionProperty` is a hardcoded literal per site (`'opacity'`, `'transform'`, `'background-color'`, `'grid-template-rows'`, …) rather than a token.

### G6 — Density is per-component, not a system concept. Confidence: primary.
`grep` finds `size?: ButtonSize` (`Button.tsx:304`), `size?: InputGroupSize` (`InputGroup.tsx:110`), and 11 `'compact'` literals. There is no `density` prop, no density token, and **no `size` on Table**. Contrast: EmptyState has a `compact` variant that shifts title `large→label` and description `body→supporting` (`src/EmptyState/EmptyState.tsx:36-73`) — the right idea, applied one component at a time.

### G7 — Truncation is handled, tooltip exists, but there is no truncate-plus-reveal composition. Confidence: primary.
Truncation is real and consistent: `textOverflow: 'ellipsis'`, `whiteSpace: 'nowrap'`, `minWidth: 0` appears together in Token.tsx:133-135, Citation.tsx:97-99, ComplexSelector.tsx:91-94, Selector.tsx:131-134, SideNavItem.tsx:77-80, SideNavItem.tsx:150. `minWidth: 0` is the flex-overflow prerequisite and core gets it.
Tooltip (`src/Tooltip/Tooltip.tsx`) has: `delay` default **200ms**, `hideDelay` default **0**, `focusTrigger: 'auto' | 'always' | 'never'` (default `'auto'` — "Only if element is naturally focusable"), `hasHoverIndication: 'auto' | boolean` rendering a **dashed underline** in `--color-border-emphasized` at `textUnderlineOffset: 2px`, and a `display: contents` wrapper so children refs survive.
**Gap: no skip-delay / grace-period model** (the 300ms-intent / 700ms-skip convention), and no documented composition that guarantees a truncated cell also gets a Tooltip.

### G8 — EmptyState is good; it is a component, not a convention. Confidence: primary.
`src/EmptyState/EmptyState.tsx`: column flex, centred, `gap --spacing-4`, `paddingBlock --spacing-8`, `paddingInline --spacing-6`; `compact` → `gap --spacing-2`, `paddingBlock --spacing-4`, `paddingInline --spacing-4`. Title = `--text-large-size` + `--font-weight-semibold` + `--color-text-primary`; description = `--text-body-size` + `--font-weight-normal` + `--color-text-secondary`; `textGroup` caps at `maxWidth: 360px`; `actions` row with `gap --spacing-2`, `marginTop --spacing-1`; `compact` flips actions to `column`. This is a shipped, well-formed empty state — a library would have to beat THIS, which most do not.

### G9 — Grid has responsive columns but no span. Confidence: primary.
`src/Grid/Grid.tsx:36-64`: `columns?: GridColumns` accepts `number` **or** `{minWidth, max?, repeat?}` for responsive auto-fit, plus separate `rowGap`/`columnGap` (`SpacingStep`) and a `rowHeight` for masonry-style row spans. The brand skill's stated workaround — "Astryx Grid has no span prop, so spans go through `style={{ gridColumn: 'span 2' }}`" — is confirmed by the absence of a span prop. **Row** spanning exists (`rowHeight`); **column** spanning does not. Asymmetry worth a recommendation.

## Astryx strengths — reject-list guardrails
Anything a library proposes that duplicates these is a REJECT, not an adopt:
- native CSS anchor positioning instead of JS measurement (G3)
- native popover top layer instead of a z-index + portal stack (G3)
- platform light-dismiss instead of a `DismissableLayer` reimplementation (G3)
- a real `EmptyState` component (G8)
- consistent ellipsis + `minWidth: 0` truncation (G7)
- a 9-step duration scale with a single named easing (G5 — the scale exists; only the *variety* of curves is thin)
