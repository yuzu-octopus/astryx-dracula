# F2 — Token architecture & dark-mode strategy: shadcn/ui, Chakra UI, Mantine, Radix Colors

## Angle

How each library layers tokens, what its dark-mode mechanism actually is, and which mechanism survives
`astryx-dracula`'s **dark-only** model (every `light-dark(a,b)` tuple pinned to `a === b`).

Fetch date for every row: **2026-09-28**. Confidence: `primary` (vendor docs/source) > `secondary` (search-summary) > `speculative`.

### C. Chakra UI v3 — token layers

C2 | Two token layers: `theme.tokens` (primitive, W3C-Token-Format-influenced, `{ value, description? }`) and `theme.semanticTokens` (`{ value, description? }`, value references another token via `{path.to.token}`). | https://chakra-ui.com/docs/theming/tokens · https://chakra-ui.com/docs/theming/semantic-tokens | primary |
C3 | **Every token value must be wrapped in `{ value: … }`.** `defineTokens` is a type-only identity function and does NOT wrap. | https://chakra-ui.com/docs/theming/tokens | primary |
C4 | Semantic colour tokens are per-colour-key × per-variant × per-mode. C5 | **7 semantic tokens per palette**, named: `solid`, `muted`, `subtle`, `emphasized`, `contrast` (aka on-solid), `fg`, `focusRing`. `contrast` is the guaranteed-legible pairing for `solid`. | https://chakra-ui.com/blog/announcing-v3 | primary |
C6 | Conditional values use an object keyed by condition: `value: { base: "…", _dark: "…" }` or `{ _light, _dark }`. Conditions must be an at-rule or parent selector. | https://chakra-ui.com/docs/theming/semantic-tokens · https://chakra-ui.com/guides/theming-customize-dark-mode-colors | primary |
C7 | `colorPalette` prop = a CSS-variable scope, swappable at any DOM depth: `colorPalette.subtle` / `.fg` / `.solid` / `.contrast`. | https://chakra-ui.com/blog/announcing-v3 | primary |

C10 | v3 removed runtime theme functions in favour of **recipes** (`defineRecipe`/`defineSlotRecipe`): `base`, `variants`, `compoundVariants`, `defaultVariants`, `slots`. ### E. Mantine — token layers

| # | Fact | Source | Conf |
|---|---|---|---|
E1 | Theme is a **plain JS object**, deeply merged with `DEFAULT_THEME`. `createTheme` / `mergeThemeOverrides`; consume via `useMantineTheme`. | https://mantine.dev/theming/theme-object | primary |
E2 | `MantineProvider` renders all theme values as `--mantine-*` CSS variables into a `<style>` tag on `cssVariablesSelector` (default `:root` + `:host`). Not a `.css` file. | https://mantine.dev/theming/mantine-provider · https://mantine.dev/styles/css-variables | primary |
E3 | Colours are **flat 10-shade tuples** (open-color + additions), `--mantine-color-<name>-<0..9>`, index 0 lightest. A colour override **must have ≥10 shades or it is a TS error** and variants break. Extra shades are allowed but unused by the default resolver. | https://mantine.dev/theming/colors | primary |
E4 | Variant vars are **computed, not static**: `--mantine-color-blue-filled` = `blue-6`, `-filled-hover` = `blue-7`, `-light` = `rgba(34,139,230,.1)`, `-outline-hover` = `rgba(...,.05)`. Doc states these "are not static, they are generated based on `theme.colors` and `theme.primaryShade`" and their values **differ per colour scheme**. | https://mantine.dev/styles/css-variables | primary |
E5 | Semantic-ish flat vars: `--mantine-color-text`, `-body`, `-error`, `-success`, `-placeholder`, `-dimmed`, `-bright`, `-anchor`, `-default`(+`-hover`/`-color`/`-border`), `-disabled`(+`-color`/`-border`). Each resolves to a different thing in light vs dark. | https://mantine.dev/styles/css-variables | primary |
E6 | `theme.other` = arbitrary passthrough object. Its documented use is a **per-scheme CSS-var map**: `cssVariablesResolver` returns `{ light: { '--x': theme.other.xLight }, dark: { '--x': theme.other.xDark } }`. | https://mantine.dev/styles/css-variables · https://mantine.dev/theming/theme-object | primary |
E7 | `deduplicateCssVariables` (**default `true`**) — a CSS variable whose value equals the default theme's is **not emitted at runtime**. This is a runtime "same as default" suppressor. | https://mantine.dev/theming/mantine-provider | primary |
E8 | `fontWeights` default = `regular: 400, medium: 600, bold: 700`. Doc's example reverts medium from 600 → 500. **Mantine ships 600 as "medium" by default.** | https://mantine.dev/theming/theme-object | primary |
E9 | `autoContrast` (+ `luminanceThreshold` default `0.3`) flips text to `theme.white`/`theme.black` based on resolved background luminosity; supports virtualColor per scheme. | https://mantine.dev/theming/theme-object · https://mantine.dev/theming/colors | primary |
E10 | `virtualColor({name, light, dark})` — explicitly "a special color whose values **should be different** for light and dark color schemes". | https://mantine.dev/theming/colors | primary |
E11 | `primaryShade` accepts `{ light: 6, dark: 8 }`. | https://mantine.dev/theming/colors | primary |
E12 | `focusRing: 'auto' \| 'always' \| 'never'` — `auto` = keyboard-only ring (native `:focus-visible`). Plus `focusClassName` / `activeClassName` global override hooks. | https://mantine.dev/theming/theme-object | primary |

### F. Mantine — dark mode (the four mechanisms that all presuppose a differing pair)

| # | Fact | Source | Conf |
|---|---|---|---|
F1 | Attribute is `data-mantine-color-scheme` on `<html>`, set by `MantineProvider` or by `ColorSchemeScript` pre-hydration. Values `light`/`dark`/`auto`; default `light`. | https://mantine.dev/theming/color-schemes | primary |
F2 | **`light-dark(a,b)` is a Mantine PostCSS function, not native CSS.** Compiles to a **duplicated declaration pair**: `.demo{color:a}` + `[data-mantine-color-scheme='dark'] .demo{color:b}`. | https://raw.githubusercontent.com/mantinedev/postcss-preset-mantine/master/README.md | primary |
F3 | Same for the `@mixin light` / `@mixin dark` pair → `[data-mantine-color-scheme='light'] .x` / `[data-mantine-color-scheme='dark'] .x`. Doc advises: define light, override with `dark`. | same | primary |
F4 | **`light-dark()` does not work on `:root`/`html`.** `light-root`/`dark-root` mixins required there. | same | primary |
F5 | `useMantineColorScheme` disables **all transitions on colour-scheme change** by default; `keepTransitions: true` opts back in. | https://mantine.dev/theming/color-schemes | primary |
F6 | Documented SSR hazard: `colorScheme` can differ client vs server (localStorage), so you cannot branch on it during SSR; use postcss `light`/`dark` mixins or `getInitialValueInEffect`. | https://mantine.dev/theming/color-schemes | primary |
F7 | Nested providers are **documented-broken**: `@mixin light` and `@mixin dark` both match one element, "whichever (light or dark) is defined **last** wins"; the order differs per component and is not stable. Maintainer `rtivital` shipped the 3-prop workaround (`getRootElement` + `cssVariablesSelector` + custom `colorSchemeManager`) and said a reliable fix "has to be built into the library itself". Discussion still shows Unanswered. | https://github.com/orgs/mantinedev/discussions/4803 | primary |
F8 | `forceColorScheme` is global-only: "if set, MantineProvider ignores `colorSchemeManager` and `defaultColorScheme`". | https://mantine.dev/theming/mantine-provider | primary |
F9 | The two-value assumption is **structural, not incidental**: PostCSS mixins, `virtualColor`, `primaryShade:{light,dark}`, and `theme.other`'s light/dark var maps are four independent mechanisms all built on "the two values differ". | F2, F3, F10, E6, E11 | primary (synthesis) |

## Dark-only survival test (the actual question)

Our model: core ships `light-dark(a,b)`; the kit overrides every tuple with one pinned dark hex, so `a === b` and light ≡ dark everywhere.

| Library | Dark mechanism | Depends on the two values differing? | Verdict under our model |
|---|---|---|---|
| **Radix Colors** | Two hand-designed files, duplicate vars on `:root`/`.light` vs `.dark` | **No** — only the *mutable alias* layer (G6) does, and that layer is optional and ours is empty by definition | **Best fit.** You ship `blue-dark.css` alone and the whole 12-step scale, the step semantics, and the Lc60/Lc90 guarantee arrive intact. The `.dark`-only scoping (G2) is the one gotcha: dark vars need the class. |
| **shadcn/ui** | `.dark` block restating every semantic token with a different hex; `next-themes` sets the class | **No** — pinning both blocks to the same hex is a legal, merely-redundant configuration | **Survives structurally.** It is our model with the `.dark` block retained. The `dark:` utility layer and `next-themes` become dead weight. |
| **Chakra v3** | `_dark` condition inside every semantic token's `value` object; `next-themes` class | **No at runtime**, but the `_dark` branch is authored into ~30+ colour tokens (C4) | **Survives, carries dead weight.** The mode branches become no-ops. Its *mode-independent* half (the 7-token semantic decomposition, `strictTokens`, `colorPalette` scoping) is the transferable part. |
| **Mantine** | `data-mantine-color-scheme` on `<html>` + PostCSS that *duplicates declarations*; `virtualColor`; `primaryShade:{light,dark}`; `theme.other` per-scheme var maps | **Yes, four ways** (F9) | **Structural dead weight.** Every one of the four mechanisms exists to swap a value, and we have nothing to swap. |

### Adopt candidates (all mode-independent; all name a concrete artifact)

1. **Radix use-case alias layer (G9)** → `astryx-theme.ts` alias block. Our `--color-tag-purple` ≡ `--color-accent` is exactly G8's "multiple aliases map to the same step" case. Add a documented alias list; **no new hex, no new token** — only a comment/declaration that names which names are aliases. *(Directly answers CoreInvertedPairAudit + GlimpseThemeResearch's `--color-tag-blue`/`--color-icon-blue` collision: Radix's sanctioned answer is either many names → one step, or a rename, and it forbids the third option, one name → two steps.)*
2. **Radix G7 naming doctrine** → applies to `--color-on-dark`, which Main has already flagged as entangled with `--color-tint-hover`. Radix's stated reason a name like `on-dark`/`card-bg` is wrong is *scope creep across use cases*, not mode. Independent, documented basis for the same conclusion.
3. **Chakra `focusRing` as a named semantic token (C5)** → our ring channel already exists as a shadow/ring family. *Needs a repo check before asserting a token name — do not invent one.*
4. **Chakra `strictTokens: true` (C8)** → `scripts/check.ts` is the existing enforcement point. Recommend a strict allowlist gate over our token names. *Main already owns `check.ts` sequencing — coordinate, do not collide.*
5. **Mantine `deduplicateCssVariables` (E7)** → **the sharpest single adopt for this brand.** Mantine ships a runtime suppressor for "variable value equals the default". Its dark-only inverse is a build-time gate: *assert every `light-dark(a,b)` in `theme.css` has `a === b` in the brand build*, using a **named constant** (Main's adopted standard) so the alpha and the label cannot drift apart as they did at `check.ts:144-145`. The redundancy becomes documented intent instead of an accident.
6. **shadcn `@theme inline` alias-not-duplicate (A5)** → already the shape of `tokens.css` as a mirror of `theme.css`. Adopt as doctrine, not as a change.
7. **Radix APCA guarantee (G4) restated per-step (G5 exception list)** → our 5-step sequential ramps should assert the *ratio each step pair produces*, with the per-hue foreground-decision exceptions enumerated the way Radix enumerates Sky/Mint/Lime/Yellow/Amber. Relevant because our brand already makes foreground a per-hue decision (Warning ships Yellow, Purple never data).

### Reject candidates (with the specific reason each loses)

| Reject | Reason | Source |
|---|---|---|
| Mantine `light-dark()` PostCSS | It *is* our model plus a second value we do not have. Compiles to a duplicated declaration pair; a same-value pair is pure bytes. | F2 |
| Mantine `virtualColor`, `primaryShade:{light,dark}`, `theme.other` light/dark maps | Three more systems whose entire reason to exist is a differing pair. | E6, E10, E11 |
| Mantine `cssVariablesSelector` + `getRootElement` + custom `colorSchemeManager` | Exists only to scope a scheme to a subtree; there is no second scheme to scope. Also the documented-broken nested case (F7). | F7, F8 |
| shadcn `next-themes` + `dark:` utility variant | Dark-only brand. `next-themes` is a JS no-flash dependency for a switch that never happens. | A7, A8, B3 |
| shadcn `--chart-1..5` categorical palette | The **dark** default is `chart-1: oklch(0.488 0.243 264.376)` — purple-first. Our doctrine: Purple is tappable, never data. A mode-dependent chart ramp is the exact pattern we forbid. | https://ui.shadcn.com/docs/theming |
| shadcn derived radius scale `--radius-sm: calc(var(--radius) * 0.6)` | Our rule is flat 5px element / 4px inner, pinned. A calc-derived scale reintroduces a second radius relationship we deliberately killed. (A6 stays a documented reject, not a defect in shadcn.) | A6 |
| Chakra `ColorModeProvider` / `LightMode` / `DarkMode` / `useColorModeValue` | Removed in v3 *in favour of next-themes*; reintroducing it re-adds a runtime mode fork. | D1, D3 |
| Mantine 10-shade colour tuples | Mantine hard-requires ≥10 shades (TS error below that). Our 5 is a deliberate compression of Radix's 3/4/5 + 9/10 into one ramp. Adopting 10 adds five unused steps per hue. | E3, G3 |
| Radix generating a *separate* dark scale | We author one file. The two-file model is the thing we do not need. (The step semantics and the aliasing doctrine from the same docs are adopted above.) | G1 |

### Mechanism notes the other F-workers should not have to re-derive

- **Mantine `light-dark()` is not native CSS `light-dark()`.** It is a PostCSS transform producing two rules. Conflating them would make us think Mantine has adopted the native function. (F2)
- **Mantine `medium` = 600 by default** (E8). Corroborates our 400/600-only rule as an established convention, and independently vindicates `--font-weight-medium` being dead: a 500 face is not a Mantine default either. *(Does not license re-adding a 500 token — the brief forbids it.)*
- **shadcn has no primitive ramp at all** (A2). Any comparison that puts shadcn's 2 layers against Chakra's 3 is comparing a ramp-less system to one with a primitive scale.
- **Radix dark vars are not on `:root`** (G2). A dark-only brand adopting Radix-style scales must apply the dark class or see nothing.
