# F5 — How real implementations handle the known-failing Dracula Comment colour

Fetch date for every source below: **2026-09-28**.

## Angle

Evidence, not opinion, on what OTHER real implementations do about `#6272A4` Comment failing WCAG AA
for body text on `#282A36`. Five sub-questions: (1) do other implementations substitute a different
Comment hex; (2) what is the Dracula team's own documented position; (3) how does the ecosystem handle
it without changing the hex; (4) is there documented practice using APCA Lc instead of WCAG ratio for
dim/muted text; (5) computed contrast arithmetic for our four lifts.

### C5 — The spec pins Comment at `#6272A4` AND mandates 4.5:1 in the same document. This is a documented internal contradiction.

- `content/spec.mdx:24` — `| **Comment** | #6272A4 | 98, 114, 164 | 225°, 27°, 51% | Comments, disabled code |`
- `content/spec.mdx:253-255` — under `### Accessibility Standards`:
  `- Maintain **4.5:1 minimum contrast ratio** (WCAG 2.1 Level AA);`
  `- Ensure color is not the sole means of conveying information;`
  `- Test against common color vision deficiencies.`
- `content/spec.mdx` also states `Current Line` and `Comment` "intentionally share the same semantic color".

By the WCAG 2.x arithmetic in §Computation A, `#6272A4` on `#282A36` = **3.03:1**. The document
therefore mandates a 4.5:1 floor and simultaneously pins a token that cannot meet it on its own
background. No exception clause, no "except Comment" carve-out, no minimum-token-with-the-floor guidance.

- Source: `raw.githubusercontent.com/dracula/draculatheme.com/main/content/spec.mdx`, fetched 2026-09-28.
- Confidence: **primary**. The contradiction is arithmetically demonstrated, not asserted.

### C9 — Documented practice in the ecosystem: ship a DEDICATED text step, not a lift of the surface colour. Radix Colors states an APCA guarantee.

radix-ui/website, `data/colors/docs/palette-composition/understanding-the-scale.mdx`:

- `:100-101` — "Steps `11` and `12`—which are designed for text—are guaranteed to **Lc 60** and **Lc 90** APCA contrast ratio on top of a step `2` background from the same scale."
- `:309` — "Step `11` is designed for **low-contrast text**."
- Steps 1–10 are surfaces, borders, solids; 11–12 are text. The low-contrast text step is a **separate
  scale step with its own contrast guarantee**, not a re-use of a border/surface step.

`https://raw.githubusercontent.com/radix-ui/website/main/data/colors/docs/palette-composition/understanding-the-scale.mdx`
— primary, fetch 2026-09-28. Rendered at `https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale`.

- Confidence: **primary**. This is the cleanest available statement of the "own your muted text token,
  and give it a measured floor" pattern.

### C10 — GitHub Primer does the same thing with WCAG numbers, and explicitly REJECTS APCA as conformance.

- `primer/primitives` dark theme, `dist/css/functional/themes/dark.css`:
  `:476` `--fgColor-muted: #9198a1; /** Muted text for secondary content and less important information */`
  `--bgColor-default: #0d1117`, `--bgColor-muted: #151b23`, `--fgColor-default: #f0f6fc`.
- `https://primer.style/product/getting-started/foundations/color-usage/` — "All contrast values for text
  and borders are calculated against `bgColor-muted` to ensure proper contrast ratios for both `muted`
  and `default`." i.e. the muted token is validated against the *harder* of the two backgrounds.
- `https://primer.style/accessibility/design-guidance/color-considerations/` — "**The APCA** … is a
  proposal and is **not normative**. In terms of WCAG, and therefore MAS-C compliance, this means that
  color contrast is valid only if it meets WCAG 2.2 criteria. A color value that is APCA-compliant might
  not be WCAG-compliant until APCA is integrated into WCAG 3.0."
- `https://github.com/primer/primitives/pull/1406` — an auditable instance of the practice: high-contrast
  themes were failing, and the fix was to move `fgColor.muted` from `base.color.neutral.8` to
  `base.color.neutral.10`, described as "the softest existing step that clears every background they face
  (including muted backgrounds) … to preserve the muted/secondary hierarchy as much as the 7:1 requirement
  allows." That is the minimum-passing-step rule, written down.

Computed (§Computation A): Primer dark `fgColor-muted #9198a1` = **6.50:1** on `bgColor-default`,
**5.94:1** on `bgColor-muted`.

- Confidence: **primary** for every URL above. Fetch 2026-09-28.

### C11 — The WCAG routes that let a 3:1 colour stay, and their exact limits.

From `https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html` (primary, fetch 2026-09-28):

- **Large text** — 3:1 instead of 4.5:1. Large-scale = "18 point text or 14 point bold text", i.e.
  ~24px / ~18.5px. `#6272A4` at 3.03:1 on `#282A36` **clears 3:1 only on the darkest tier** — on
  Floating `#343746` it is 2.51:1, which clears *nothing*.
- **Incidental** — no contrast requirement for text that "are part of an inactive user interface
  component", pure decoration, or invisible-to-anyone. `#6272A4`'s own spec usage string is
  "Comments, **disabled code**" — disabled is precisely the SC 1.4.3 "inactive component" carve-out.
  That carve-out covers *disabled controls*, not general editorial text, and cannot be stretched to it.
- **Thresholds, not round numbers** — "the computed values should not be rounded (e.g., 4.499:1 would
  not meet the 4.5:1 threshold)". This kills any "it's basically 4.5" argument; see §Computation A where
  `#8288A6` lands at 4.0832:1.
- **User-mechanism escape (G174)** — the criterion's "Situation A/B" technique list names
  `G174: Providing a control with a sufficient contrast ratio that allows users to switch to a
  presentation that uses sufficient contrast`. Primer cites the same technique
  ("All Day and Night sub-themes do not need to meet WCAG color contrast requirements, provided all
  default Day and Night theme content is accessible. This guidance is derived from WCAG 2.2 Technique G174").
- 1.4.3 explicitly extends to **placeholder text and hover/focus text** — so "it's only a hint" does not
  exempt a muted token in an input.

`L = 0.2126·R_lin + 0.7152·G_lin + 0.0722·B_lin`, ratio `= (L_lighter + 0.05)/(L_darker + 0.05)`.
Executed locally (`/tmp/f5/wcag.py`, Python; cross-checked in JS, identical to 4 dp).

### C13 — Computed APCA Lc values (COMPUTATION, not citation)

Method: `apca-w3@0.1.9` — the implementation the W3 Silver group lists as the code intended for public
guidelines — `APCAcontrast(sRGBtoY(txt), sRGBtoY(bg))`, run locally. Negative = light text on dark
background (the WoB/"dark mode" polarity).

| Foreground | on `#282A36` | on `#343746` | on `#21222C` |
|---|---|---|---|
| `#6272A4` Comment | **Lc 25.1** | Lc 21.9 | Lc 26.5 |
| `#8288A6` base-muted | **Lc 35.3** | Lc 32.0 | Lc 36.7 |
| `#9AA1BC` secondary | **Lc 47.8** | Lc 44.6 | Lc 49.3 |
| `#B0B3C4` paragraph | **Lc 57.6** | Lc 54.4 | Lc 59.1 |
| `#4C5067` subdue | **Lc 10.7** | Lc 7.4 | Lc 12.1 |
| `#F8F8F2` Foreground | Lc 99.0 | Lc 95.8 | Lc 100.5 |

Against APCA's own published use-case levels (Myndex/SAPC-APCA, `documentation/README.md` and
`APCA_in_a_Nutshell.html`, primary, fetch 2026-09-28):

- `Lc 90` preferred for body-text columns · `Lc 75` minimum for body text · `Lc 60` minimum for content
  text that is not body/column/block text · `Lc 45` minimum for larger/heavier text (36px normal or
  24px bold) · **`Lc 30` "the absolute minimum for any text not listed above … placeholder text and
  disabled element text"** · `Lc 15` "the absolute minimum for any non-text" and "designers should treat
  anything below this level as invisible".

Reading the table against those levels:

- **`#6272A4` at Lc 25.1 is below Lc 30 — APCA's absolute floor for *any* text, including the
  spot-readable cases (disabled text, placeholders) that WCAG exempts entirely.** WCAG exempts the
  category APCA most tolerates; APCA does not.
- `#8288A6` (Lc 35.3) sits just above that floor, consistent with its WCAG failure — the two models
  agree here.
- `#9AA1BC` (Lc 47.8) lands between the Lc 45 larger-text minimum and the Lc 60 content-text minimum.
- `#B0B3C4` (Lc 57.6) is the only lift within 2.4 Lc of the Lc 60 content-text floor.
- `#4C5067` (Lc 10.7) is below Lc 15, i.e. **in APCA's own words "should be treated as invisible"** —
  which supports the existing "chrome only, never text" rule with a number rather than a preference.

**Important caveat, and it is decisive for how this is used:** APCA is *not* normative. GitHub Primer
states plainly that "color contrast is valid only if it meets WCAG 2.2 criteria" (C10). APCA is a
diagnostic that re-ranks the same colours, not a licence to ship one WCAG fails.

- Confidence: **computed** (values) / **primary** (level definitions and the normative status).

## Conflicting evidence

1. **Spec mandates 4.5:1 vs spec pins a 3.03:1 token** (C5). Both statements are in the same file,
   `content/spec.mdx` at `:24` and `:255`. Neither is a different condition or a stale copy — they
   genuinely conflict, and no third source resolves which governs. The org's own ports (C1) resolve it
   in practice in favour of the pinned hex. **Carried forward as: the hex wins, the 4.5:1 line is
   aspirational, and any implementation that wants the 4.5:1 line must add tokens the spec does not
   define.** No maintainer statement was found either way.

2. **APCA as a design tool vs APCA as a conformance standard.** Radix builds its low-contrast text
   step's contract on APCA Lc 60 (C9). GitHub Primer states APCA "is not normative" and that only
   WCAG 2.2 governs (C10). Both are primary, both are current, and they are not in conflict on the
   facts — they occupy different roles (design target vs conformance test). **Carried forward as: APCA
   is admissible for setting and justifying a muted-text target; it is not admissible for claiming
   conformance.** Primer's own numeric practice (validate the muted token against `bgColor-muted`, the
   harder background) is the transferable part.

3. **The "no substitution" finding vs. three substitutions.** C1's negative holds for *code* themes in
   the dracula org. It does not hold for the org's non-code surfaces: zed's Alucard variant (C3), the
   dracula.com site (C4), and the Alacritty port (C8) all change it. **Carried forward as: within the
   code-theme contract, `#6272A4` is untouchable; outside it, the org has never treated it as
   untouchable.** The distinction is scope, not contradiction.

4. **Reported figure conflict on `#6272A4` on `#282A36`.** A web search returned an assistant-summarised
   "approximately 3.06:1" (secondary, untraceable to a computation). My computed value is
   **3.0260:1** (§Computation A). **Carried forward as 3.03:1**; the 3.06 figure is discarded as
   untraceable, and the 0.03 difference does not change any verdict.

## Computation A — WCAG 2.x method (stated, because the numbers are load-bearing)

Formula, per WCAG 2.x and W3C's own "Notes on formula" in the SC 1.4.3 Understanding doc:

```
C_lin = C/12.92                     if C <= 0.04045
C_lin = ((C + 0.055)/1.055)^2.4     otherwise
L     = 0.2126*R_lin + 0.7152*G_lin + 0.0722*B_lin
ratio = (L_lighter + 0.05) / (L_darker + 0.05)
```

Every foreground and background `L` used is listed inline in C12. No value in this report is estimated.

## Computation B — HSL→hex for the dracula.com site tokens

Standard HSL→sRGB conversion, executed locally. `#8B82C4`, `#22212C`, `#B2AFC0`, `#C2C0CE`, `#0E0D11`,
`#383645`, `#635D98`. Rounded to 8-bit, so ±1/255 of the source expression. The source of truth is
the HSL string; the hex is a convenience for the ratio arithmetic.
