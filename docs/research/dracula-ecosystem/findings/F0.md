spacing rule and no derivation anywhere in the file.

|---|---|---|

### C2 — The spec's opaque current-line fallback `#353747` is NOT in our palette.

`spec.mdx:54-57`, verbatim:
> If the target editor only supports an opaque (solid) line highlight, use these fallback
> line-highlight colors:
> - **Dracula Classic**: `#353747` (same fallback used in dracula/cursor)
> - **Alucard Classic**: `#E2DECA`

`spec.mdx:59`: "These fallback values are implementation guidance for line highlight rendering
only. They do not add new syntax tokens to the official palette."

- Source: same URL, lines 54-59 · Fetch 2026-09-28 · Confidence: **primary**
- Meaning: the only OPAQUE line-highlight colour the spec names for the dark theme is
  `#353747`. We do not ship it. Our Current Line handling is `#6272A4` (the alpha-overlay
  route), so we are compliant with `spec.mdx:52` and do not *need* `#353747` — but it is
  sanctioned, and it is the one hex a consumer must reach for when `!alpha` is unavailable.
  Relevant to us only if we ever target a non-alpha-capable renderer (print, some PDF,
  certain terminal emulators).

## Addendum, second pass, same angle (own grep, 2026-09-28) — this REWRITES C1's practical meaning

### C7 — `#191A21` is ALREADY IN OUR THEME. It is the shadow and scrim hue, and nothing else.

The spec's missing "Background Darker" tier is not an absent colour. It is a colour we use
constantly and never expose as a token.

`grep -nE '#[0-9A-Fa-f]{8}' tokens.css` (32 matches):

| line | token | value | meaning |
|---|---|---|---|
| `:156` | `--shadow-low` | `0 2px 4px #191A210D, 0 4px 8px #191A211A` | shadow at 5.10% + 10.20% |
| `:157` | `--shadow-med` | `0 2px 4px #191A210D, 0 4px 12px #191A211A` | same |
| `:158` | `--shadow-high` | `0 4px 6px #191A211A, 0 12px 24px #191A2126` | 10.20% + 14.90% |
| `:173` | `--color-overlay` | `#191A21CC` | scrim/dim at 80.00% |

- Source: local `tokens.css:156-158,173` · Fetch 2026-09-28 · Confidence: **primary**
- **Every shadow and the overlay scrim in the kit is already composited from the spec's
  Background Darker.** The hex is in our codebase 4 ways and in the token list 0 ways.
  So the human's question is NOT "do we adopt `#191A21`" — it is "does `#191A21` become a
  named surface tier, or does it stay an implementation detail of shadows?" Promoting an
  already-shipped hex to a token is a far cheaper decision than a new hex, and the
  candidate list should say so rather than listing `#191A21` as if it were new.

### C8 — INTERNAL INCONSISTENCY: `--color-shadow` is `#21222C`; the shadow implementations are `#191A21`.

`tokens.css:182` declares `--color-shadow: #21222C` and `astryx-theme.ts:115` pins the same
(`pin('#21222C')`). But `--shadow-low/med/high` (`tokens.css:156-158`) are built from
`#191A21`, and `--color-overlay` (`:173`) is `#191A21` too. **The token named as the shadow
colour is not the colour any shadow uses.**

- Source: local `tokens.css:156-158,173,182` + `astryx-theme.ts:115` · Confidence: **primary**
- Skill conflict, flagged not fixed: `skill://astryx-dracula` states the flat-crisp shadow
  hue is `--color-shadow` (`#21222C`). The built CSS uses `#191A21`. Either the token is
  declared-but-unused, or the skill is wrong. Read-only slice — not resolving. Belongs to
  the theme/tokens owner.

### C9 — Our complete measured alpha ladder: a discrete, hand-picked 8-stop ladder

`grep -oE '#[0-9A-Fa-f]{8}' tokens.css | sort -u` → 32 unique 8-digit hexes over 11 base
colours. Decoded (alpha = byte/255), computed not estimated:

| hex tail | byte | **actual %** | what it is | where |
|---|---|---|---|---|
| `0x0D` | 13 | **5.10%** | shadow blur 1 | `--shadow-low/med` |
| `1A` | 26 | **10.20%** | state wash surface + shadow blur 2 | `--color-background-<hue>` ×10, shadows |
| `1F` | 31 | **12.16%** | overlay hover | `--color-overlay-hover: #0000001F` |
| `26` | 38 | **14.90%** | shadow blur 3 | `--shadow-high` |
| `30` | 48 | **18.82%** | inset ring | `--shadow-inset-*` ×5 |
| `33` | 51 | **20.00%** | overlay pressed | `--color-overlay-pressed: #00000033` |
| `4D` | 77 | **30.20%** | state wash border | `--color-border-<hue>` ×10 |
| `CC` | 204 | **80.00%** | scrim | `--color-overlay` |

- Source: local `tokens.css`, 2026-09-28 · Confidence: **primary** (own arithmetic)
- Three label corrections, stated with their derivation:
  - **Inset ring family is 18.82%, not 30%.** `0x30` = 48/255. Independently confirms
    Main's ruling; the audit report should carry the number, not the label.
  - **The skill's "12% / 20%" hover/press is 12.16% / 20.00%.** `0x1F`=31, `0x33`=51.
    20% is exact; 12% is 0.16% over. Immaterial to rendering, material to a gate that pins
    a number.
  - **The wash spine IS 30%.** `0x4D` = 77/255 = 30.20% borders, `1A` = 10.20% surfaces.
    Two genuinely different families; not one mislabelled ladder.
- Relevance to this slice: this is a **discrete, hand-picked 8-stop alpha ladder that exists
  in no Dracula source**. Not a continuous ramp, not derived from any spec number, not
  `!alpha` from dracula/cursor's ladder. The technique inventory has to rule on whether a
  self-invented alpha ladder is safe to keep, and against what.
